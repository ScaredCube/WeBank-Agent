# 小We · F-03 收藏金融数据隐私与持久化决策审查

日期：2026-11-01
版本范围：`feature/ip-object-workspace`，含此前尚未提交的 Pre-PR 整改
状态：**信息流已核验，低风险修复完成；正式存储架构仍待团队产品/安全决策。**

## 1. 实际数据流（源码审查）

`SaveBillCard` 接收后端可信账单 Tool 结果，先通过 `billSchema`、`billResultCard` 生成只读金融卡片；点击「收藏」后，经 `store.saveSnapshot` 按 `userId:snapshotId` 写入浏览器 IndexedDB `webank-ui-snapshots/snapshots`。这不是后端 API 存储。

实际存储内容包括：
- 卡片标题、来源（账户名称、已脱敏尾号、月度等）和观测时间；
- `metric` 分单位金额、`bar_chart` 分类金额、`list` 中的格式化金额文字；
- 可信调用方提供的会话/助手消息引用 `origin`；
- 可刷新账单时保存的 `refresh.accountId` 和月份。
- 过滤掉卡片 `action` 块、未知多余字段、部分长数字/临时占位符；本轮进一步过滤误入展示文本的 token/Authorization/Bearer 格式。

`CollectionPanel` 从本地 IndexedDB 按用户数值标识读取，显示卡片，可删除单项或清空当前用户全部收藏；如已保存刷新规范，手动调用经过鉴权的银行账单 API 更新本地卡片。原始助手财务结果另有 **后端 MessageResult 加密保存**，两套持久化不能混为一谈。

`AuthProvider.logout()` 清除 localStorage 中的登录凭证和本次 React 用户状态，但**不会清除 IndexedDB 收藏**。收藏隐私开关仅控制 React 展示；不是加密。不同 userId 在 UI 级分区，但同源脚本/设备使用者仍可读取浏览器持久化记录，`userId` 也不是服务器授权凭证。

## 2. 威胁模型与结论

| 威胁场景 | 现状 | 风险 |
|---|---|---|
| 单用户本地模拟银行比赛演示、个人电脑 | 卡片金额可留存，离线可查看 | 接受前须知晓明确的本地存储范围 |
| 同一设备切换登录用户 | UI 按数值 userId 分区 | 本地数据仍可经浏览器同源存储直接读到，非安全隔离 |
| 共享设备 / 已退出登录 | 本地收藏仍存在 | 敏感金额/账户线索可能暴露 |
| XSS / 第三方同源脚本 | 可以访问 IndexedDB | 现有前端脱敏规则无法阻止已执行的同源脚本读取 |
| 本地设备未经授权访问 | 数据未加密 | 浏览器磁盘缓存泄露风险 |
| 从旧版本升级 | 已存在的本地卡片会继续保留 | 此轮不静默删除或宣称已迁移旧缓存 |
| 模型或页面意外把操作令牌放入卡片文本 | 新的保存路径新增 token 格式遮盖，结果 Tool 本身不应包含令牌 | 辅助防护，并不构成完备的敏感信息识别机制 |

因此 **F-03 不能仅凭渲染隐藏、字符串遮盖、用户 ID 分区或测试通过而关闭**。

## 3. 本轮已执行的最小范围整改

1. `SaveBillCard.tsx` 在用户保存前显示精简但真实的告知：本地保存含金额、未加密，退出后仍保留。
2. `CollectionPanel.tsx` 用清楚的本地数据说明替换了原先较空泛的“个人空间”副文案，指出隐藏金额不影响底层存储，明确清空入口。
3. `store.ts` 的展示文本保存前额外遮盖 `account_token`、`source_token`、`target_token`、`recipient_contact_token`、`confirmation_token`、`API_KEY`、`Authorization`、`Bearer` 等典型凭证表示；不影响数值块、模拟刷新和既有卡片结构。
4. `store.test.ts` 补充一项测试：意外混入的令牌字符串不持久化，预期金额仍保留。
5. 保留已有删除、清空、刷新与收藏来源跳转行为，不自动删除用户历史收藏；未改动后端数据库、金融工具、账号会话模型或生产部署配置。

测试：收藏与页面相关前端定向测试 **74 passed**；`npm run build` 通过；Lint 0 errors、1 条既有 WorkspacePanel 警告；没有在真实浏览器使用实际用户账号手动验收。

**本次措施是透明告知 + 降低误存凭证风险；不是金融收藏静态加密。**

## 4. 可选产品架构（需团队选择）

### A. 比赛模拟版继续使用本地 IndexedDB（本批默认保留）

- 只允许使用**隔离合成数据**；产品 UI 明确提示本地保存、退出仍保留且未加密；用户可以在收藏面板一键清空。
- 保留离线收藏、手动刷新、轻量前端实现；不会新增数据库迁移。
- 不应在 PR/部署文档中宣称多用户存储隔离或真实财务数据安全。需要团队明确部署边界及演示数据来源。
- 适用于短期内部/比赛 Demo，**不适用于存储真实个人银行数据的产品版本**。

### B. 浏览器只保存来源指针，打开时按鉴权重新读取服务端加密结果

- IndexedDB 只保留 ID、源会话/消息编号和必要排序元数据；金融结果仍由后端已加密的 `MessageResult` 解密，并按登录用户的会话权限返回。
- 需要增加指定历史消息的鉴权获取或定位 API、前端异步恢复；历史源失效、离线浏览、收藏“更新数据后与原始结果不同”的语义要重定。
- 可显著减少本机金额明文持续保存，但若功能要求收藏脱离原消息存在，就不够。

### C. 服务端用户归属 + 加密收藏（推荐面向真实用户的长期方案）

- 新建或扩展后端收藏实体：`user_id`、收藏 ID、加密结果快照、来源标识、保存/刷新时间、状态版本。创建/查看/刷新/删除均验证用户身份；直接复用已有 `vault` 加密服务。
- 以用户账号为数据归属，在服务端保持历史版本与跨设备恢复；前端仅保留短期会话缓存，避免长期本地明文。
- 代价：新增 API、持久化 Schema、迁移、回滚、权限、幂等、配额和后续维护，必须与本轮已形成的 F-01 数据库迁移门禁一起设计；不宜未经团队确认就在临近 PR 时插入。

**我的建议：** 本次面向隔离模拟银行数据的比赛 PR 暂采用 A，并显式限制使用范围；一旦准备面向真实金融数据或正式多用户上线，应单独规划 C 的纵向 PR。若团队尤其重视轻量架构且可接受收藏必须依附历史消息，B 是中间路径。

## 5. 决策和合并门槛

**当前尚未冻结的项目决策：**
1. 比赛版本是否明确限定为合成银行数据？是否会部署到公用机器/公网？
2. 收藏是否需要跨登录、跨设备长期保留？旧数据是否必须在脱离原会话后继续可读？
3. 维护者是否批准 A 作为比赛限定实现并接受 IndexedDB 未加密及历史缓存清理责任？
4. 若采用 B/C，服务端新增接口、Schema 迁移与前端缓存迁移的 owner 和 PR 依赖顺序是什么？

在团队明确批准模拟范围以前，F-03 标注 **局部风险已降低，存储架构待决策**。如需将真实或用户输入的金融数据持久保存，本项应列为部署阻断，不应仅用一行 UI 提示代替安全设计。
