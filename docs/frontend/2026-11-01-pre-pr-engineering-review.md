## 正向发现：值得保留的设计

1. **服务端信任边界明确。** `backend/app/api/routes/chat.py` 对账户、银行卡、联系人引用重新核验归属；账户/卡身份由服务端绑定，模型不能直接授权目标账号。
2. **业务执行与用户确认分离。** `backend/app/services/transfer_service.py` 将准备、确认和执行拆开；执行层重查令牌、账户状态、余额和事务；`operation_service.py` 使用 SQLite `BEGIN IMMEDIATE` 序列化高风险写操作。上述是当前模拟环境有价值的安全约束。
3. **可信结果数据链路。** `backend/app/api/routes/chat.py` 只接受服务端 Tool 返回的账单与银行卡快照，使用加密快照恢复历史；前端 `bill-result-card.ts` 对结果进行 Schema 验证。没有直接信任 LLM 生成卡片金额。
4. **中断与幂等方向合理。** `chat_submissions.py` 通过 `(user_id, request_id)` 唯一约束、HMAC 指纹和显式状态收敛限制重复请求；客户端使用 `sessionStorage` 保存非敏感请求标识，只查询状态、不自动重放资金操作。
5. **交互价值明确。** 对象引用支持点击/拖动/`@` 搜索；桌面/手机采取不同交互方式；会话、银行卡和账单结果的衔接已形成可用的差异化产品能力。

## 审查发现（附证据、影响及建议）

### F-01 · P1 / 影响发布：迁移入口与自动建表存在时序和覆盖缺口

**证据：** `backend/app/main.py` 的 `lifespan()` 调用 `init_db()`；`backend/app/db/session.py:init_db()` 执行 `SQLModel.metadata.create_all()`。但 `backend/scripts/check_chat_schema.py` 的 `TARGETS` 只有 `conversationselection` 与 `chatsubmission`；本分支的 `backend/app/models.py` 还新增了 `MessageResult`（`messageresult`）表。

**影响：** 如果先启动新版应用，新表可能已由 `create_all` 自动创建，迁移工具会判为无需处理，升级前备份流程也不会发生；现有字段变更及旧结构差异也不能由 `create_all` 自动迁移。已有演练仅覆盖受控 SQLite 新建表，不足以作为团队正式迁移方案。

**建议：** 设立独立的数据库升级入口和清晰的“迁移完成后才能启动”条件；审查全部新表与索引；在升级前执行备份、模式检查、回滚演练，禁止把自动建表当成正式迁移机制。补齐 `MessageResult` 的迁移核验。**本项在涉及持久化数据的 PR 前应解决**。

### F-02 · P1 / 影响对话可信度：无工具自然语言的安全保护依赖有限正则

**证据：** `backend/app/agent/loop.py` 在没有 Tool 结果时释放 `response_policy.tool_free_reply()` 的模型文本；`backend/app/agent/response_policy.py` 主要通过 `_ACTION_COMPLETION`、`_BANK_FACT` 等正则阻止伪造金融信息。

**影响：** 恢复自然对话是合理修复，但正则无法全面表达自然语言语义。例如“款项已汇出”“余额大概五千块”等不一定符合现有模式，却可能传达未经核验的业务结论。反过来，关于普通金融知识的金额举例可能被误判为个人银行数据。现有 3 个真实模型场景 + 固定离线用例不能证明错误率可接受。

**建议：** 由确定性的请求类型/服务端状态决定是否允许“无 Tool 金融事实”类回答；将模型自由回复限定为问候、产品能力解释和参数追问，金融账户/操作状态只能依据已核验 Tool 输出；建立对抗样例、误拦截与漏拦截指标，以及回滚路径。**Guard Prompt 不应为了自然度而放宽。**

### F-03 · P1 / 隐私产品决策：收藏的金融数值以明文保存在浏览器存储

**证据：** `frontend/src/features/collections/SaveBillCard.tsx` 将真实已验证的账单结果转换为卡片后调用 `saveSnapshot()`；`frontend/src/features/collections/store.ts` 使用 IndexedDB `snapshots` 保存 `card.blocks`；`sanitizeLeaf()` 对 metric/bar_chart 数值不加密，list 的金额文本也可持久保存。隐私模式仅在组件渲染层隐藏信息。

**影响：** 本机 IndexedDB 的账单余额/收支/消费类别可被同源脚本及设备本地环境读取；`userId` 分区与视觉隐藏不能作为本地数据加密或跨设备访问控制。对于纯模拟演示有可接受的产品选择空间，但团队必须知道这是**本地非加密缓存**，明确生命周期、共享设备风险和数据处理要求。

**建议：** 合并前与团队明确收藏的信任边界与模拟数据限定，优先考虑最小字段/清理策略；若接入非模拟用户数据，应设计服务端存储或可靠加密、登录退出清理和跨设备策略，不应将当前 IndexedDB 当成金融数据长期存储方案。

### F-04 · P1 / 性能与伸缩性：历史会话读取是无界全量查询，并存在 N+1 快照查询

**证据：** `backend/app/services/chat_service.py:list_conversations()` 与 `list_messages()` 均使用 `.all()` 且不分页；`backend/app/api/routes/chat.py` 列表中的每个助手消息都调用 `_present_message()`，后者单独查询 `MessageResult`；`frontend/src/features/chat/useChatController.ts` 每次发送结束后通过 `Promise.all([api.messages(...), api.conversations(...)])` 再取完整历史。

**影响：** 随每个会话的历史消息数 `M` 增长，最少需要传输/处理 O(M) 消息，且约有 O(助手消息数) 的附加结果查询；长期使用时前后端成本、渲染开销及感知延迟会累积。此为**静态复杂度判断，未进行性能压测或宣称具体耗时**。

**建议：** 分页/游标化历史接口、批量读取快照（避免 N+1），发送后优先增量更新、按需同步历史；定义常规和长会话基准样本并测量网络/SQL/渲染耗时。合并前至少确认容量目标和性能预算，重要慢路径有清晰的改造计划。

### F-05 · P1 / 发布配置前置条件：模拟默认配置与正式部署必须显式隔离

**证据：** `backend/app/core/config.py` 仍默认 `debug=True`，演示账号/口令及固定验证码；`backend/app/api/routes/auth.py:/auth/demo-account` 在 `debug` 为真时返回演示凭证；`backend/app/api/routes/bank_data.py:/accounts/demo` 只以 `settings.debug` 为演示开户开关；`frontend/src/lib/auth.tsx` 使用 `localStorage` 持久化 JWT。

**影响：** 这些能力多属于**团队既有演示架构而非全部由本分支引入**，但作为公开可访问服务的默认设置存在明显风险。代码合并与生产上线是不同门槛：目前可限于受控的合成数据演示环境，不可据此宣称真实银行/公网环境安全。

**建议：** PR 明确 `DEBUG=false` 等生产配置门禁；部署必须配置密钥、关闭演示凭证端点与固定验证、限制登录尝试；评估 Cookie/CSRF 与现有 JWT 存储模型的替代方案。**公开联网部署前为 P0 阻断**。
