## 完成的产品能力

### 输入框 `@` 对象搜索
- 用户在真实聊天输入框输入 `@`，按中文名称、银行名称、脱敏尾号或对象类型检索当前用户可见的账户、银行卡与联系人。
- 从现有的经过授权的 `/bank/dashboard` 与 `/cards` 获取候选数据；只列出可用的人民币账户、关联账户有效的卡片、有效联系人。当前不提供尚无类型化授权协议的持仓。
- 搜索按会话与数据刷新标识进行缓存；普通聊天不额外加载对象目录；服务端继续按对象类型、归属及可用状态核验每一项引用。
- 用户可使用方向键、回车、鼠标选择候选，Esc 关闭；输入法合成期间不抢键盘，尚未加载完成时回车不误发送；选择后剥离 `@` 查询文本，仅保留可移除的对象胶囊。
- 保留原有拖入对象、点击引用、跨会话草稿与新建会话时的输入连续性。

### 同一条回复的多个可信金融结果
- 一次 Agent 回复可按调用顺序承载多个只读银行 Tool 结果，目前支持 `get_monthly_bill`、`get_card_status`，最多 8 项。
- 后端只接收已经由真实银行 Tool 执行、经过 Pydantic 校验及权限限制的数据，不将模型自行描述的金额或卡片状态作为结果。
- 单项结果继续用旧版 `MessageResult` kind 存储；多项使用同一张表的 `kind=tool_results` 并加密保存类型化列表，不需重建现有表或迁移旧记录。
- `GET /chat/conversations/{id}/messages` 经会话所有权检查和 `Cache-Control: no-store` 返回解密且验证后的列表，旧 `bill_result` 和 `card_result` 接口兼容保留。
- 前端复用现有账单图表与银行卡状态卡，严格限制类型、顺序和数量；刷新及切回历史仍展示同样的结果，不生成重复卡片。
- 多项受支持查询的助手说明收敛为一句话，由结构化卡片承载数据。

## 边界
- `@` 搜索目前限账户、银行卡、联系人；持仓仍需另做服务端对象协议。候选项并不构成授权，交易继续通过已有单独确认和风险验证执行。
- 多结果目前涵盖账单和银行卡，最多 8 项。其他只读 Tool 逐步接入前需定义严格输出 schema 与数据生命周期。
- 旧 `MessageResult` 仍以一条助手消息对应一份密文记录；当前使用单密文多结果格式。正式上线还应补充数据库迁移管理、密钥轮换与数据保留策略，并进行真实 LLM 与 Guard 端到端测试。
- UI 风格：少用次级说明，靠布局建立对象与结果的关联。
