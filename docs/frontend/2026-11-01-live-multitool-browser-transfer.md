## 发现的实际工程问题

1. **模型复写银行卡身份不可靠**：与上一轮账户引用同类问题。已在 Chat Route 经持有人及卡到账户关联核验后，传递 `verified_card_id`；AgentLoop 对已通过字段白名单验证的 `get_card_status`，以服务端经核验的 `card_id` 和 `account_token` 替换模型输入。未授权对象无此绑定。
2. **部分成功结果丢失**：真实模型在完成查询后额外发起 `calculate` 等无效工具，可能达到工具轮数限制。原 SSE 报 `error` 并丢失已有成功卡片。现在存在已验证 `trusted_results` 时发送明确的部分完成文案及 `done`，加密保存已成功的结果；完全没有可信结果时维持旧的显式错误协议。绝不把未完成工具伪装成成功。
3. **模型对转账对象的引用 Token 不能可靠复写**：真实模型正确调用 `prepare_transfer`、Guard 允许，但联系人 Token 错误导致服务端拒绝。对于同时经用户明确选择、服务端核验的付款账户和收款联系人，以及含明确“转账/汇款/打款”和金额的请求，将受控 `source_token`、`recipient_contact_token` 与收款姓名绑定到 `prepare_transfer`。模型仍确定动作类型和金额；参数白名单、Guard、身份匹配、单独确认和执行权限全部保留。
4. **金融安全反例**：带“不要确认或执行”的模糊表述被现有注入检测识别为 verification_bypass；后续使用明确的“先生成待确认操作，我要核对”安全表达做验收。未修改注入检测规则。

## 真实模型金融转账准备验收

使用另一个隔离的真实模型 ASGI HTTP 场景，传入本人模拟账户和已核验联系人，要求准备 1 元模拟转账：

- Guard 审核通过，银行 Tool 成功创建 1 条 `pending` 记录，产生 `action_required` 和 `done`；
- 账户余额保持原值；
- **没有调用**确认、执行、扣款接口；没有真实资金流动。
- 约 4.1 秒（单次样本，不是性能承诺）。浏览器端的风险确认弹窗仍需要补做真实模型人工验收。
