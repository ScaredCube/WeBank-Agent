# 小We · F-04 长会话加载与查询复杂度整改

日期：2026-11-01
分支：`feature/ip-object-workspace`，基线 `f405bdd` 之后的未提交整改
类型：Pre-PR Engineering Review · 性能与数据访问复杂度
范围：模拟银行会话、可信结果快照、React 历史导航；不接触真实银行数据库

## 原始问题与结构分析

第一轮审查 F-04 指出：
- 后端 `list_messages()` 每次无条件加载会话全部消息 `M`。
- `_present_message()` 对每条助手消息单独查询一次 `MessageResult`（典型 N+1）。
- 前端打开会话以及每次发送后都重新请求完整会话历史。

原有 N+1 结构的 SQL 次数约为 1 次历史查询 + A 次助手消息的结果快照查询（A 为助手消息数），请求包与 React 历史解析成本均随全部历史长度增长。此结论来自静态源码和 SQL 事件计数，不是外部服务器的性能跑分。

## 本轮改动

### 后端 · 兼容旧客户端的 keyset 分页

`GET /api/chat/conversations/{conversation_id}/messages` 保持原始默认 JSON 数组语义；新增可选：
- `limit`：1—100 的消息数量。
- `before_id`：排他式游标，必须与 `limit` 同时出现；只读取该消息 ID 之前的历史。
- 返回仍按 ID 正序（旧到新），最近页由服务端倒序索引查询 + 翻转产生。
- 继续先校验当前登录用户对会话的归属；缓存头保持 `no-store`。
- 结果快照以一批 SQL 根据助手消息 ID 查询并绑定，使用大小不超过 400 的参数批次，避免 SQLite 绑定参数上限；加密解密仍通过已有 `vault` 与 Schema 验证，无法解密的历史消息按旧策略局部降级。
- 旧客户端未带参数时仍会收到完整历史，以保证历史调用方的兼容性。此兼容行为**仍有无界载荷风险**，应在 API 版本升级和客户端全面迁移后单独设定废弃窗口。

### 前端 · 渐进加载且保留原 UX

- 浏览器初次打开历史默认请求 51 条，只呈现最近 50 条，多出的 1 条用于推断是否显示“加载更早消息”。
- 点击加载更早消息时带当前最早 ID 游标，再取最多 50 条；通过滚动锚点修复前插后页面跳动。
- 完成一次发送后只回读最近 1 页，并合并先前用户明确展开的旧记录，避免重复下载全部历史或意外删除已读记录。
- 收藏卡片定位来源若早于最近页，则在用户明确触发的导航动作中按需翻页查找（最多 20 页，每次不超过 51 条），不让普通会话加载产生额外长尾成本。超过上限的极长历史链接仍可能无法自动定位，应在后续容量与 UX 设计中考虑目标 ID 定位 API。

## 复杂度与权衡

- 新版初始页面：历史查询/网络/前端解析的单次数据上限为 51 条，与已保存的完整历史总数解耦；消息列表初始渲染不再一次展开整条长会话。
- 数据库查询：批量读取结果快照，SQL 查询数约 `ceil(A/400)`，而非 `A`；客户端默认页的 A 不超过 51。
- 按需加载全部历史仍会随累计阅读量增长；明确的“加载更早消息”是用户触发行为。
- 收藏来源自动寻址额外请求有 20 页上限（最坏约 1000 条），这是当前比赛场景的保护限额，非“无限长历史精准定位”保证。

## 剩余质量审查事项

1. `GET /conversations` 的会话列表仍一次全量返回，属于潜在扩展成本，尚待产品容量目标。
2. 旧消息接口未传 `limit` 仍保持无界响应，后续需 API 兼容策略和迁移窗口。
3. `MessageList` 的累计渲染总数随着用户不断点击“加载更早”仍增长；真正数万条长会话需要虚拟列表或窗口管理，但会增加滚动/定位复杂度，当前缺少比赛规模证据，不建议直接引入。
4. 对超过 20 页的收藏来源建议后续增加经会话鉴权的指定消息定位或邻近窗口查询。
5. 需要在 PR 阶段用固定硬件、固定内容和不同消息长度记录真实响应/内存/React 渲染耗时。SQL 查询次数降低**不能直接推导端到端延迟提升百分比**。
