# 小We · 第十七批：Agent 请求幂等与断线状态核验

日期：2026-11-01
代码分支：`feature/ip-object-workspace`，在独立 Git worktree 开发。团队原分支无改动。

## 为什么需要这一层

聊天 SSE 中断后，客户端可能并不知道后端是否已完成 Tool 调用或创建了待确认操作。历史聊天服务曾经仅依靠前端“先核对历史”的提示；银行工具本身有部分幂等键，但重新发起 Agent HTTP 请求会生成新的请求上下文，因此仍可能产生另一笔新的待确认操作。

## 本轮实现

### 1. 请求身份与服务端去重

- `ChatRequest.request_id`：可选、受限格式的幂等请求标识。新版前端每次发送使用浏览器安全 UUID；本次发送中断后，**在同一个挂载会话内**同一内容和引用再次提交将复用原 ID。变更内容、对象或明确开始新请求会产生新 ID。
- `ChatSubmission`：数据库唯一索引 `(user_id, request_id)`，登记所属会话、受密钥保护的 HMAC-SHA256 原文/引用指纹、状态和历史消息/待确认动作 ID。不会保存原始消息正文、引用 Token、确认 Token 或模型密钥。
- 在写入用户消息、创建银行对象 Token、调用模型/Tool **之前**原子登记请求；重复请求在服务端终止，不会第二次执行 Agent，也不会生成第二个操作准备幂等键。
- 同 ID + 不同正文/引用或跨会话复用：HTTP 409，拒绝重新执行。跨用户请求隔离，必须先验证当前会话归属。
- 已完成只读回复：同 ID 返回持久化助手消息的单个 `done` SSE 事件，结果可从加密历史恢复。重新发送不会再次调用 Tool。
- 已生成待确认动作：同 ID 仅发送安全的 `action_warning` 和 `done(null)`。不再发 `action_required`，**不再下发原确认令牌**；用户需到操作记录核对。
- processing/interrupted/failed 或已知未确定：重复请求返回 409，强制先核对，不在网络恢复时自动再次执行。
- 原有 `request_id` 缺失的老客户端仍可运行，但**不具备这一层聊天去重保证**。正式接入应统一升级客户端。

### 2. 状态核验与前端恢复

`GET /api/chat/conversations/{conversation_id}/requests/{request_id}`

只允许请求所属用户访问所属会话，响应禁用缓存，返回 `state`、用户消息 ID、待确认操作 ID，以及已完成回复中权限过滤后的历史消息。不会返回银行受控 Token 或待确认动作确认令牌。

前端在网络断开或收到未知错误时主动查询这一接口：

- 若状态为 completed：从历史恢复已保存的回复，避免误报“发送结果不确定”；
- 若为 action_pending：只提示已建立待确认操作，并要求在操作记录核对，不自动重新确认；
- 如仍不可确定：保留原文和同一请求 ID，提示用户核对历史再决定下一步。

全局刷新会重新创建前端组件，当前仅保证服务端同 ID 去重和单次挂载周期内的 ID 复用；**尚未跨页面刷新保存未完成请求 ID 的本地恢复关联**。也不自动重连并重新执行 Tool，这是后续可以完善的体验问题。

### 3. 事务与安全边界

- 数据库唯一约束负责并发请求的最终仲裁；测试覆盖同 ID 双线程竞争，只有一次领取成功。
- 服务端记载状态：processing、completed、action_pending、failed、interrupted。即使模型/网络中断也不会自动重新执行旧 ID；尚不具备长时任务恢复/任务队列机制。
- 保留原有账户/卡/联系人持有人校验、Guard 审核、转账金额一致性、确认和执行分离；所有金融验收数据均为合成银行环境。
- `ChatSubmission` 是新数据库表，现有 `SQLModel.metadata.create_all` 测试环境可建立；真实团队数据库集成前必须完成结构迁移、数据库备份与可回滚验收。
- 如果实际财务业务准备成功但进程在标记状态前崩溃，会保留保守的 processing/interrupted 状态；**不重试旧请求**，应人工对照操作记录和银行幂等业务记录。

- TokenDance `deepseek-v4.1-flash-1017` 账单首次查询成功，重复相同 ID 只收到 `done`，历史消息不重复。
