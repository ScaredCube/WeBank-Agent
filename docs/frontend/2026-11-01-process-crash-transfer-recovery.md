# 小We · 第二十一批：进程崩溃与金融确认恢复演练

日期：2026-11-01
开发分支：`feature/ip-object-workspace`
性质：**跨进程故障注入 + 数据持久化验收**。不连接任何真实银行或真实 LLM。

## 新增资产

- `backend/scripts/rehearse_agent_process_crash.py`：创建一次性隔离 SQLite，启动独立 Python 子进程，按场景在预设故障点执行真正的 `os._exit(87)`，随后由另一个新进程启动 FastAPI 应用并查询持久数据。
- `backend/tests/test_process_crash_rehearsal.py`：在 pytest 中调用整个四场景演练，同时验证脚本不能操作任意数据库路径。

运行：

```powershell
cd backend
uv run --group dev python scripts/rehearse_agent_process_crash.py
```

### 四个必须成立的安全不变量

| 故障点 | 重启后必须观察到 |
|---|---|
| SQLite 扣款事务尚未提交 | 自动回滚，账户余额不变，没有转账或账务记录 |
| 转账待确认动作已提交、回复尚未送达 | 恰好一笔 pending，余额不变，未经用户确认不能执行 |
| 用户确认记录已提交、执行尚未发起 | 初始余额不变；必须由一个新、明确的执行 API 请求才扣款一次 |
| 转账执行事务已提交、响应尚未送达 | 重试执行返回同一交易回执，不生成第二条转账交易 |

所有场景还验证：
- ChatSubmission 恢复为 `interrupted`，**相同 request ID 重发返回 409**，不自动重新调用 Agent。
- 经过真实业务准备接口再次提交**相同转账幂等键**时，仅返回已存在的转账 ID，不重新下发单次确认令牌。
- 服务端启动触发既有 stale 请求恢复；只将离线合成数据库中的请求时间加速到超过 30 分钟。该演练**没有实测等待 30 分钟或监控真实活跃 worker**。
- 账户、待确认动作、模拟交易表及交易最终状态与预期逐一核对。
- 结果 JSON 仅包含公开的测试标签和检查结果，不输出任何确认令牌、银行引用 Token 或密钥。

### 重要能力边界

本次使用真实 SQLite 事务、真实 `prepare_transfer` / `confirm_pending_action` / `execute_transfer` 业务代码和 FastAPI 的 HTTP 测试客户端；用独立进程强制退出验证**已提交 / 未提交事务的持久性**。

它仍是**可控时间点的进程故障注入**，不等于真实云端部署中的网络分区、负载均衡重试、多副本抢占、硬件故障、外部支付清算或第三方银行生产环境验收。正式比赛交付前还要完成浏览器高风险确认 UI、授权策略及最终部署检查。

本次只新增隔离演练工具和测试，不需要迁移数据库，也没有改动团队正式服务、模型密钥或生产金融逻辑。
