# 小We · F-02 Agent 无 Tool 回答可信边界整改

日期：2026-11-01
状态：功能候选已实现，仍需独立二轮审查及团队合并批准。

## 审查依据与原问题

此前 `app/agent/response_policy.py` 的首层决策完全依赖对模型文本的正则匹配：
- 未查银行 Tool 时，“余额大概五千块”或“款项已经汇出”可能被放行；
- 用户询问一般金融知识时，“假设投资100元，一年收益5元”的示例金额会被误拦截。
这同时削弱金融可信性和对话自然度。单纯增加匹配词无法构成授权证明。

## 本轮实现

`app/agent/response_policy.py` 新增 **NoToolScope** 分类，**根据用户本轮消息**区分：
- `CONVERSATION`：普通交流可展示模型自由回复，仍需通过内部标识/敏感令牌及异常内容保护。
- `EDUCATIONAL`：普通金融知识与假设案例可以自然解释并使用教学示例金额，但不拥有真实金融状态权威。
- `PRIVATE_READ`：涉及个人账户、账单、银行卡、交易、持仓等信息；若当前轮没有可信 Tool 结果，只能回复服务端提供的查询提示，**不能使用模型生成的个人金融事实**。
- `ACTION`：涉及本轮准备或执行操作；无 Tool 结果由服务端按转账、挂失、理财、订阅给出必要条件及确认流程，不把“模型说已办好”当成业务状态。
- `ACTION_STATUS`：询问此前转账或其他操作是否成功；没有相关状态核验就明确说**尚未核实**，不能把“不知道结果”误说成“没有成功”。

当服务端已验证并选中了某金融对象，但用户本轮请求模糊时，默认进入私有查询范围；明确问候不受影响。模型文本始终按轮缓冲，通过边界检查后再发 SSE，避免未审查的文本逐字输出。对于已有 Tool 结果、金融卡片数据、Guard、模拟交易的权限及一次性令牌逻辑，本轮没有改动。

**注意：** `classify_no_tool_request` 是有限词表的保守输入路由，仍不能覆盖所有中文表达；`_ACTION_COMPLETION` 等输出模式是辅助检查，不可作为金融交易授权或自然语言语义保证。不能以这些测试通过宣称所有幻觉消失。长期更理想的方向是从前端意图及工具调用状态生成强类型任务/结果协议，减少对自然语言识别的依赖。

## 质量与性能评估

- 不引入数据库、模型或网络依赖，也不添加 LLM 二次审核开销。
- 对单轮用户文本按固定数量的词表线性扫描，复杂度与用户文本长度近似线性，额外内存为常数级（有限规范化字符串除外）。模型自由文本仍保留已有限长 1200 字符和敏感标记保护。
- 容易发生误分流的边界包括：含多个业务意图的复杂句、口语省略、教育问题混合具体账户、用户不显式说明“查询”却要求报数。应作为下一轮独立评审样例而非单次绝对保证。
- 在没有任何可信 Tool 的场景，服务端会保守地要求查询/核对，可能牺牲个别金融问题的自然度，但不会因为模型未经验证的执行声明而推进资金操作。
