# T-302 模拟卡片状态与挂失

状态：后端卡片针对性测试 11 passed，完整回归 102 passed（隔离临时数据库和模型替身），前端未接线，真实模型效果未验证；仅供模拟演示，实际短信、真实银行及生产强验证均未实现。

每个演示账户对应一张模拟卡。启动会为已有演示账户幂等创建缺失卡片，不覆盖账户余额或流水；无需删除旧数据库。卡片状态为 `active`（正常）或 `lost`（已挂失），账户状态另行维护。若卡片缺失、已挂失或不可用，则禁止该账户准备及执行尚未完成的模拟转账；已完成转账的幂等查询不撤销既有结果。

所有接口需要 Bearer 登录令牌，状态与挂失接口的成功响应返回 `Cache-Control: no-store`。归属在服务端校验。

1. `GET /api/cards` 返回当前用户卡片列表：`card_id`、`account_name`、`masked_number`、`status`、`account_status`；查询绿色自动执行。
2. `POST /api/cards/{card_id}/loss/prepare` 创建红色待验证动作，返回 `action_id` 和一次性 `confirmation_token`；此时卡片仍正常。无权访问、已挂失、不可用或未开启演示验证时拒绝。
3. `POST /api/actions/{action_id}/verification/start`，请求 `{"token":"..."}`；再调用 `POST /api/actions/{action_id}/verification/verify`，请求 `{"token":"...","code":"..."}`。验证成功仍不改变卡片状态；仅 `DEBUG=true` 的固定测试码演示，不是真实短信。
4. `POST /api/cards/loss/{action_id}/execute`，在锁内检查当前用户、动作类型、验证成功和有效期、账户和卡片状态；成功后返回 `{"card_id":1,"status":"lost"}`。同一成功动作重复执行返回原结果；另行发起已挂失卡片的挂失被拒绝。

Agent 可使用 `get_card_status` 查询，`prepare_card_loss` 只发送包含后端动作和一次性令牌的 `action_required` 事件；令牌不返回模型或保存到对话历史，聊天文字不能代替验证或执行。前端必须调用独立执行接口并以其返回结果为准，不得伪造挂失成功。查询、准备、验证、执行及拒绝写入审计；成功挂失和审计同事务。直接接口请求无会话关联。

聊天结果分别展示卡片状态和账户状态；账户冻结或状态未知时不得据卡片“正常”推断可以转账。准备接口**没有幂等键**：重复请求可能产生多个动作及不同令牌，前端不应把它们视为同一个请求。多个动作均验证后，只有第一个成功执行并改变卡片状态；其他动作执行返回 400，保留原申请记录。同一个已成功动作的重复执行返回原结果。

挂失和转账在 SQLite 写事务中按取得锁的顺序执行：挂失先提交时，未执行转账被拒绝；转账先提交时，扣款与流水保留，之后挂失不会撤销。并发测试使用受控线程，未覆盖多进程或其他数据库。

目前每账户最多一张模拟卡；挂失影响该账户所有本项目模拟转账，是演示限制，不代表真实银行多卡规则。银行卡解挂、补卡、真实银行网络、前端界面及真实多因素验证均不在本批范围。
