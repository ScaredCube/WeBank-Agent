# T-203 异常熔断与限流

状态：后端基础完成。2026-10-29 运行 `tests/test_security.py` 5 passed，完整后端回归 177 passed；未调用付费模型。

## 目标

按用户累计连续失败并临时锁定，同时对敏感接口做固定窗口限流。锁定、限流、自动解锁和手动解锁都必须可审计。实现仅覆盖当前单用户 SQLite 演示，不替代生产级风控、验证码或分布式限流。

## 数据模型

新增 `SecurityState`：

| 字段 | 说明 |
| --- | --- |
| user_id | 用户主键，一会话一行 |
| failure_count | 当前失败窗口内连续失败次数 |
| failure_window_started_at | 失败窗口起点，UTC |
| locked_until | 锁定截止时间，可为空 |
| request_count | 当前限流窗口内敏感请求数 |
| request_window_started_at | 限流窗口起点，UTC |
| updated_at | 最后更新时间，UTC |

表由启动时 `create_all` 创建，无需删除已有数据库。

## 失败计数与锁定

计入失败的行为：

- 用户输入命中注入规则（T-204）；
- 子 Agent 护栏拒绝（T-202，仅 `guard_denied`，护栏故障不计入用户失败）；
- 验证码校验失败；
- 待确认动作确认失败（错误令牌、过期、已处理或越权）。

规则：

1. 默认 600 秒窗口内连续失败 5 次触发锁定；
2. 默认锁定 900 秒；
3. 窗口过期后从 1 重新计数；锁定过期后清除锁定和失败计数；
4. 锁定期访问敏感接口返回 HTTP `423`，中文提示“账户因连续失败暂时锁定，请稍后再试或使用解锁流程。”；
5. 锁定状态下的请求仍写 `security_lock_denied` 审计，但不重复增加失败次数。

## 接口限流

默认每个用户 60 秒内最多 60 次敏感请求，固定窗口计数。

应用范围：

- `/api/chat/*`
- `/api/actions/*`
- `/api/transfers/*`
- `/api/cards/*`

超限返回 HTTP `429`，中文提示“请求过于频繁，请稍后再试。”，并写 `security_rate_limited` 审计。登录、账单、审计查询和解锁接口不在当前限流范围。

## 解锁路径

1. **自动过期**：锁定时间结束后，下一次敏感请求会清除锁定并写 `security_unlocked`，原因 `lock_expired`。
2. **手动模拟解锁**：`POST /api/security/unlock`，请求 `{"code":"<演示解锁码>"}`。仅 `DEBUG=true` 可用，固定解锁码由 `SECURITY_UNLOCK_CODE` 配置，默认 `246810`；错误码返回 400。成功后写 `security_unlocked`，原因 `manual_unlock`。
3. 手动解锁只清除锁定和失败计数，不清除限流窗口计数；限流窗口按自身时间过期。

固定解锁码仅用于本地演示，不是生产认证机制；`DEBUG=false` 时整个模拟解锁路由不可用。

## 配置

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SECURITY_FAILURE_THRESHOLD` | `5` | 触发锁定的连续失败次数 |
| `SECURITY_FAILURE_WINDOW_SECONDS` | `600` | 失败计数窗口 |
| `SECURITY_LOCK_SECONDS` | `900` | 锁定时长 |
| `SECURITY_RATE_LIMIT_REQUESTS` | `60` | 每用户每窗口敏感请求上限 |
| `SECURITY_RATE_WINDOW_SECONDS` | `60` | 限流窗口 |
| `SECURITY_UNLOCK_CODE` | `246810` | 仅演示的手动解锁码 |

## 审计

新增事件：

- `security_failure`：结果 `failed`，原因 `failure`；
- `security_locked`：结果 `locked`，原因 `failure_threshold`；
- `security_lock_denied`：结果 `denied`，原因 `account_locked`；
- `security_rate_limited`：结果 `denied`，原因 `rate_limit`；
- `security_unlocked`：结果 `success`，原因 `lock_expired` 或 `manual_unlock`。

审计不保存用户输入、工具参数或解锁码。

## 并发与边界

- SQLite 下使用 `BEGIN IMMEDIATE` 串行化计数更新；未实现 PostgreSQL 行锁方案。
- 仅按用户计数，不做 IP / 设备维度限流，也不限制登录失败。
- 固定窗口限流存在窗口边界突刺；不是令牌桶或滑动窗口。
- 锁定只作用于上述敏感路由器；账单、审计查询等只读接口仍可用。
- 手动解锁码是演示配置，不能视为生产安全能力；生产需要独立管理通道、权限校验和密钥管理。
- 失败计数来源于当前已实现的四类事件；后续新增业务需要显式接入，不会自动统计所有异常。
