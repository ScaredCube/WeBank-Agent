# 安全自评报告

## 1. 报告概述

本项目是一个嵌入银行 App 的 AI 智能体入口：用户用自然语言描述需求，Agent 负责理解意图与组织流程，所有真实业务动作由后端固定代码执行。安全设计的总原则是对用户输入和 AI 模型零信任——安全控制完全依赖固定代码而不是 AI 决策，AI 不直接接触银行 API。

本报告包含三部分：

1. 权限分级实现说明（第 2～4 章）：绿/黄/红三级风控的设计与落地方式，以及围绕它的支撑性安全机制；
2. 已知风险清单（第 5 章）：当前版本已识别的风险与限制，逐条说明影响与缓解；
3. 结论与改进计划（第 6 章）。

评估方法：以设计文档为判级基准，逐项核对后端源码与测试结果。

## 2. 零信任安全架构

### 2.1 信任边界

| 主体 | 信任设定 | 说明 |
| --- | --- | --- |
| 浏览器 / 前端 | 不可信 | 所有实体归属、风险等级、余额、日累计均由服务端固定代码校验；前端只提交实体 ID，不提交令牌或权限凭证 |
| AI 模型（LLM） | 不可信 | 模型只能提出工具调用意图，不能决定权限、不能改写金额与收付款方、不能从工具结果或结构化引用获得真实卡号 |
| 用户自由文本 | 不可信数据 | 可进入模型上下文，但不构成业务授权；含卡号/手机号时同样如此；不进入LLM护栏审查层的上下文，降低提示词注入风险 |
| Tool 层与数据库 | 唯一可信执行点 | 唯一可解析令牌、唯一可执行扣款的地方；所有写业务有事务边界 |
| 系统提示词 | 服务端固定 | LLM护栏不拼接用户输入；用户文本只以 `user` 角色进入模型 |

### 2.2 核心设计原则

1. **AI 不直接接触银行 API**。所有业务由后端 Tool 层执行，LLM 只能提出调用意图；工具必须注册元数据（名称、描述、参数 Schema、风险等级）才可被调用。
2. **权限分级由固定代码判定**，不由 LLM 决定。绿色自动执行、黄色用户确认、红色强验证。
3. **用户确认必须由服务端校验**。确认弹窗、验证弹窗是硬编码固定组件，不是 Generative UI；用户对 AI 说"确认"无效，模型自由文本不能代替确认。
4. **不做通用代码执行与沙箱**。需要计算时只提供受限计算工具（基于 Python `ast` 的纯数值求值），禁止完整 Python / Shell 运行环境，也禁止 LLM 自行计算数字。
5. **禁止编造**。账户、余额、交易结果只能来自 Tool 返回值；无 Tool 结果时，模型不得以自由文本建立任何金融事实。
6. **操作审计与熔断是必做项**，所有关键决策链路（工具调用、风控判定、确认、验证、执行、拒绝、锁定）均写入持久化审计。
7. **失败默认拒绝**。护栏异常、令牌解析失败、密钥缺失、审计失败等异常一律中止或升级，不降级为"直接执行"。

### 2.3 工具分层

- **核心业务用 Tools**（转账、查账单、卡片挂失、理财申购等）：增加安全性，保证数据库事务一致；Tool 直接调用 service 层，不经过 HTTP 数据接口。
- **银行数据只读接口（`/api/bank/*`）不注册为 Agent Tool**，LLM 不能直接调用，仅供前端页面展示；Agent 业务操作使用独立路径（`/api/wealth/*` 等）。
- **外部生态联动（MCP）** 为规划项，接入时必须纳入风控与审计，外部故障不影响核心业务。

## 3. 权限分级实现说明

### 3.1 风险等级定义（与赛题要求对照）

| 级别 | 执行策略 | 典型操作范围 | 赛题要求 | 本项目实现 |
| --- | --- | --- | --- | --- |
| 绿色 | 自动执行 | 余额查询、交易记录查询、账单分析、理财收益查询等纯查询类操作 | Agent 确认意图后直接执行，无需二次确认 | 9 个绿色只读 Tool + 受限计算器，服务端判级通过后直接执行并写审计，受频率限制 |
| 黄色 | 用户确认 | 小额转账（日累计 ≤ 1000 元）、订阅查询/取消、虚拟卡申请等 | 执行前展示操作详情并获得明确确认 | 准备 Tool 只创建待确认动作；固定确认弹窗 + 服务端一次性令牌确认；确认与执行分离，执行前二次风控 |
| 红色 | 强验证 | 大额转账（日累计 > 1000 元）、密码修改、卡片挂失/解挂、理财产品申购等 | 须通过人脸识别、短信验证码或 U 盾等多因子认证 | 红色准备 Tool 创建待验证动作；两级强验证：密码/验证码、密码+人脸；验证通过后执行前再次复查 |

判级依据是 `backend/app/risk/engine.py` 中的固定代码：工具基础风险等级来自注册元数据，转账类按整数分金额与服务端查询的当日累计分级（不信任模型传入的累计值），夜间（北京时间，默认 00:00–06:00，可配置）将黄色升级为红色，绿色查询不因夜间自动升级。判定只升不降。

### 3.2 绿色：自动执行

- 只读 Tool（余额、交易、月度账单、卡片状态、理财产品/持仓/风险测评、订阅查询/识别）与受限计算器 `calculate` 注册为绿色。
- 工具执行循环有次数限制（最多 3 轮、每轮最多 5 次调用），防止无限循环与探测。
- 查询结果由后端固定代码格式化输出；不出现模型口算的数字。
- 绿色也必须有审计记录（`tool_called` / `risk_assessed` / `tool_result`），并受接口频率限制。

### 3.3 黄色：用户确认

- 对外转账、内部转账（>1000 元）、收款请求、取消订阅等准备 Tool 只创建**待确认动作**（`PendingAction`），不直接执行业务。
- 服务端生成**随机一次性确认令牌**：数据库只保存令牌哈希，不保存明文；令牌绑定用户、黄色风险、待确认状态与有效期（默认 300 秒），原子更新防止重复或并发确认。
- 确认接口只记录确认；执行是**独立接口**，执行时在 SQLite `BEGIN IMMEDIATE` 写锁事务内重新校验确认有效期、令牌绑定、账户状态、余额与日累计，任何一项不符即拒绝并回滚。
- **聊天文本"确认"不能扣款**：确认必须携带服务端下发的一次性令牌，且令牌不返回给模型、不写入会话历史。
- 确认弹窗展示的账户、收款人来自服务端数据库的脱敏字段，不展示完整卡号。

### 3.4 红色：强验证（两级）

按设计目标，红色强验证划分为两级：

1. **密码/验证码**：大额转账等基础红色动作，须通过模拟验证码验证；
2. **密码+人脸**：卡片挂失、理财申购/赎回/持仓转换等默认要求密码+模拟人脸；护栏升级也可把其他红色动作提升到人脸级。

验证机制设计要点：

- 每个动作最多一个验证会话；重复启动不重置失败次数；验证码错误三次锁定；有效期不超过动作有效期。
- 仅存验证码 HMAC 摘要，不存或记录明文；明文验证码不出现在日志。
- 验证成功后状态变为 `verified`，仍需独立调用执行接口；执行时重新检查动作与验证有效期、余额及风险，红色动作不会降级为只需普通确认。
- 风险升级保护：执行前重新判级，若风险已从黄色升级为红色，拒绝执行并要求重新发起验证。
- 当前版本的验证码与人脸均为模拟实现（演示固定测试码，仅 `DEBUG=true` 时可用），真实短信、真实人脸识别与 U 盾等生产多因子验证未接入；本报告按设计目标描述分级体系，能力边界统一见第 5 章。

### 3.5 内部转账业务例外（按设计确认的业务口径）

**本人名下、同银行账户**之间的内部转账是资金不流出本人的操作，经人工确认采用以下口径：

- 按北京时间当日累计判定：当日累计不超过 1000 元为绿色，超过 1000 元或单笔超过 1000 元为黄色；
- 不升级红色（含夜间），因为资金不流出本人；
- 不占用对外转账的 1000 元日累计额度，两类流水分开统计，避免混算；
- 服务端校验归属、余额、账户与卡片状态；跨行同名账户归集不享受该例外（按对外转账处理，当前版本不实现跨行归集）；
- 绿色内部转账同样有审计记录并受频率限制，金额必须与用户原文做确定性比对，无法确定或单位有歧义时降级为黄色确认；
- 内部转账绿色路径由 Tool 在服务端复查后直接执行，不由模型自行计算余额或风险。

### 3.6 外部环境风控因子

- 夜间时段（北京时间）黄色升红已实现，起止整点可由服务端环境变量配置并校验。
- 定位、IP 置信度、设备指纹等更多环境因子为规划项，接入时同样以固定代码判定，不交给 LLM。
- 独立子 Agent 护栏在每次工具调用前结合北京时间与本轮历史工具调用，识别夜间高风险动作、只读查询后异常切换目标、短时间连续高风险动作、重复准备/探测等模式（见 4.2）。

### 3.7 AI 护栏与风险升档

设计目标是"每次调用工具时都使用独立会话的子 Agent 进行检查"。实现方式：

- 护栏只接收服务端生成的行为摘要（工具名、用途描述、基础风险等级、参数安全摘要、历史工具调用记录、服务端时间），不传用户原文、姓名、备注、手机号、卡号或令牌正文。
- 护栏拒绝或异常时，不直接拦截，而是把固定代码风险提升一档（绿→黄、黄→红、红密码→红密码+人脸），并写审计。
- 护栏是 LLM 判定，存在非确定性；最终安全边界始终是固定代码的注册表、参数校验、风控、确认与事务边界。

### 3.8 执行前二次风控

所有模拟写业务（转账、内部转账、收款、挂失、理财申购/赎回/转换、取消订阅）的执行接口均遵循同一模式：

1. 进入 SQLite `BEGIN IMMEDIATE` 写锁事务；
2. 重查动作状态、有效期、验证/确认状态；
3. 事务内解析数据令牌并复查归属、账户状态、余额、卡片状态与当日累计；
4. 重新执行固定代码风控判级，风险升级即拒绝；
5. 扣款/状态变更、流水、成功审计在同一事务提交；任何失败整体回滚，拒绝/回滚后的失败记录在独立事务写入。

### 3.9 前置意图绑定（拖拽交互的权限约束）

负一屏拖拽生成的前置意图按设计强制约束模型行为：

- 前端只提交动作与来源/目标实体 ID，不提交标签、token 或金额；
- 服务端重新校验实体归属、状态与碰撞矩阵（六种已定义组合；未定义组合直接拒绝，不调用 AI）；
- 服务端生成不可枚举令牌并注入 token 化前置提示词；提示词不写入历史；
- 模型调用的工具必须与意图动作一致，来源/目标 token 与金额由服务端覆盖，模型不能替换；模型给出的金额必须与用户原文提取值一致，否则拒绝。

## 4. 支撑性安全机制

### 4.1 幻觉防护

- 账户、余额、交易结果只能来自 Tool 返回值；工具结果由后端固定代码渲染。
- 无 Tool 结果时，服务端输出策略（`response_policy`）区分普通交流、教学解释、个人金融查询、操作准备和既往操作状态：个人账户查询、资金操作和既往操作状态必须来自 Tool 或明确说明"未核实"，不得以模型正文建立金融事实。
- 需要计算时只提供受限计算工具，LLM 不得自行计算数字。
- 可信结果事件（`bill_result`、`card_result` 等）只由成功的绿色 Tool 产生，模型自由文本不能制造。

### 4.2 注入防御

- 模型调用前对用户文本做 NFKC 归一化、移除零宽字符、压缩空白后匹配固定规则，覆盖指令覆盖、验证绕过、风险篡改、越狱/开发者模式、角色覆盖、提示词泄露和角色边界标记；命中后不调用模型、不执行工具并写 `input_blocked` 审计。
- 历史消息读取时再次检测，命中内容替换为拦截标记，防止旧消息重新进入模型上下文。
- 工具参数按注册 Schema 白名单校验：只允许注册字段、标量类型，限制字符串长度并拒绝非法控制字符；失败写 `invalid_arguments` 审计。
- 系统提示词固定在服务端，不拼接用户输入。

### 4.3 操作审计

- 关键节点（用户输入拦截、工具调用、风控判定、确认、验证、执行、令牌解析、锁定/解锁）均写持久化审计，字段与事件受白名单约束。
- 审计不保存用户输入摘要、参数、身份凭证或敏感数据；不记录完整卡号、手机号、密文或密钥。
- 扣款、流水与成功审计同事务；审计失败时业务不会报告成功。
- 提供按用户隔离的只读查询接口 `GET /api/audit`，操作记录可按会话追溯。

### 4.4 异常熔断与限流

- 用户级连续失败锁定：注入拦截、护栏拒绝、验证码错误、确认失败计入连续失败；默认 600 秒内 5 次锁定 900 秒，锁定期敏感接口返回 423。
- 敏感接口固定窗口限流：`/api/chat/*`、`/api/actions/*`、`/api/transfers/*`、`/api/cards/*` 默认 60 秒 60 次，超限返回 429。
- 自动过期解锁与手动解锁均写审计；手动解锁码仅为演示机制。
- IP / 设备维度限流与登录失败限流为后续增强项（见风险清单）。

### 4.5 敏感数据令牌化去敏（Data Tokenization Vault）

设计目标：模型永远不接触真实卡号与手机号。

- 账户、联系人、理财持仓等持久实体使用不可枚举的用户级令牌（随机部分 128 bit 以上，如 `<CARD_7F3K9Q2M...>`），禁止 `<CARD_01>` 这类可枚举编号；令牌按用户隔离，跨用户不可复用。
- 用户本轮输入中的手机号/卡号可生成请求级临时令牌，带有效期（默认 10 分钟），仅绑定当前用户与当前请求。
- 令牌只在 Tool 层事务内解析（`resolve` 校验归属、类型、吊销状态与有效期）；解析失败直接中止并回滚，错误提示与"实体不存在"一致，避免枚举探测。
- 查询工具只返回脱敏号码、实体 ID 或令牌；工具参数白名单拒绝包含原始长号码的字段。
- 密文使用 Fernet（带认证加密），独立数据加密密钥与版本，不复用 JWT 密钥；支持版本化轮换，轮换不得导致令牌失效，缺失旧密钥时 fail-closed。
- 审计只记录令牌与实体 ID，不记录密文、明文或可逆密钥；`token_resolved` / `token_resolve_denied` / `token_revoked` 事件均可追溯。
- 用户主动输入的内容按原文展示与保存（设计确认的取舍，尝试过正则匹配但很容易造成误匹配），但不构成业务授权；工具边界仍保持令牌化。

### 4.6 受限计算工具

- 基于 Python `ast` 的纯数学表达式求值器，不使用 `eval`；只接受数字、括号和 `+ - * / // % **`。
- 拒绝变量、函数、属性、下标、容器、控制流、导入、布尔、复数与字符串；限制表达式长度、AST 节点数、求值时限、整数位长、浮点范围和指数。
- 结果由后端固定渲染，不使用模型自由文本。
- 不做通用代码执行与沙箱——计算之外的权限一律不提供。

### 4.7 认证与凭证

- 密码使用 Argon2 哈希；登录错误提示不区分账号不存在与密码错误。
- JWT 鉴权，会话与消息接口均校验归属关系；跨用户数据不可见。
- 确认令牌、验证码、数据加密密钥、HMAC 密钥均不落入日志、会话历史或模型上下文。

## 5. 已知风险清单

以下风险按影响域分类列出，均为当前版本已识别、在文档中如实记录的项。**统一能力边界声明**：当前版本为比赛模拟演示，强验证（验证码/人脸）、熔断限流、数据令牌化生命周期与风控规则均为模拟实现，未接入真实短信、真实人脸、U 盾、真实银行接口与生产级风控；生产环境部署前必须接入真实多因子验证与生产级风控，并完成团队签收。

### 5.1 强验证与凭证

| 编号 | 风险 | 影响 | 缓解 / 边界 |
| --- | --- | --- | --- |
| R-01 | 红色强验证为模拟实现（固定测试码、模拟人脸），未接入真实短信/人脸/U 盾 | 红色分级在演示环境可信，生产环境不成立 | 仅 `DEBUG=true` 可用；红色动作仍受服务端确认链路、事务内二次风控与审计约束；真实多因子验证列为交付前必做 |

| R-19 | 固定回复兜底已移除，最终聊天文本由 LLM 生成；`ReplyGroundingVerifier` 本身也是 LLM，复核结果非确定性 | 模型可能在无 Tool 依据时说出余额、金额或“已执行”，复核存在漏判 | 结果卡仍是最终事实源；复核不通过让主模型重写，仍不通过返回 `error`，不展示候选文本；风控等级与工具授权不受文本复核影响；真实模型漏判率待验证 |

| R-22 | `DATA_ENCRYPTION_KEY` / `DATA_HMAC_KEY` 缺失或失效时，可信结果快照无法加密持久化 | 该轮结果卡刷新后不可恢复，可能让用户误以为操作未发生 | 助手文本和提交状态仍持久化，不因快照失败丢弃回答或让对话轮空；结果卡以当前页面和操作记录为准；生产部署必须配置独立数据密钥 |
| R-23 | 短确认“是/好的/确认”会复用上一轮已校验前置意图 | 用户可能是在回答其他问题，或对象状态已变化；错误复用可能准备非预期动作 | 只接受短确认文本且没有新的引用/意图；复用前重新校验账户、联系人、持仓、金额和状态；动作准备后立即清除；资金执行仍必须经过固定确认/验证弹窗，聊天文本不能直接执行 |
| R-24 | 操作结果回复由独立的 `ACTION_REPLY_PROMPT` 在弹窗结束后生成 | 模型可能错误描述已完成/已取消状态或金额 | 终态由服务端 `PendingAction.status` 读取，客户端不能自报成功；回复只接收白名单动作事实；生成失败只保留服务端完成卡，不写固定兜底 |

## 6. 结论与改进计划

### 6.1 结论

本项目按"对 AI 零信任"的设计目标建立了完整的安全框架：

- **权限分级由固定代码判定**，绿/黄/红三级与赛题要求对齐；黄色确认与红色验证均为服务端校验的固定组件，模型与用户聊天文本均无法绕过。
- **AI 全程不接触银行 API**，模型只能通过受元数据约束、白名单校验、护栏审查和风控判级的 Tool 提出意图；所有资金动作在写锁事务内完成二次风控与审计。
- **数据令牌化与脱敏边界**保证模型、SSE 事件与审计日志中不出现真实卡号/手机号。
- 幻觉防护、注入防御、操作审计、熔断限流、受限计算等机制形成纵深防御。
- 固定对话回复兜底已移除；最终文本由 LLM 生成并经独立 `ReplyGroundingVerifier` 复核，GenUI v2 由 AI 生成并经独立 `ViewReviewer` 复核，可信结果卡仍是最终事实源。

同时必须如实说明：当前版本的强验证、熔断限流与令牌生命周期为模拟演示实现，真实多因子验证、真实银行接入、生产级风控与部署加固尚未完成，能力边界以第 5 章风险清单为准。

### 6.2 改进计划（按优先级）

1. 合并后复核签收：完成 R2-01/F-02 Agent 独立评审；团队签收 F-01 数据库预检、F-03 收藏隐私范围、F-05 生产配置隔离、F-09 CI/PR 门禁。
2. 数据与意图安全：补齐 T-207 令牌生命周期（自动吊销、过期清理、密钥运维）。
3. 真实强验证：接入真实短信/人脸等多因子验证，替换演示固定码。
4. 生产级风控：IP/设备维度限流、登录失败限流、分布式限流；补充定位、IP 置信度等环境因子进风控引擎。
5. 多用户体系与 token 吊销、PostgreSQL 迁移。
7. 剩余智能增强：DAG、长期记忆、多模态、MCP，逐项纳入风控与审计。
