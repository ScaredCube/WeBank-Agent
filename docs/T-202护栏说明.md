# T-202 子 Agent 调用前护栏

状态：后端基础实现完成。2026-11-01 调整：所有工具仍必须经过 LLM 护栏；护栏不再直接拒绝调用，而是把固定代码风险提升一档（绿→黄、黄→红、红密码→红密码+人脸）。`GUARD_SYSTEM_PROMPT` 同时明确只读查询在工具/用途/风险一致且参数摘要正常时应放行，减少误拒。`tests/test_guard.py` 9 passed；使用模型替身，未调用付费模型。真实模型下的护栏判定质量、延迟和误拒率尚未验证。

## 目标与边界

每次 Agent 准备执行 Tool 前，先用独立上下文进行一次安全审查。护栏只判断“这次工具调用行为是否可疑”，不执行工具；可疑时由固定代码把风险提升一档，最终是否确认、验证、执行仍由固定代码和用户完成。

护栏输入只包含服务端生成的结构化摘要：

- 工具名与服务端注册的用途描述；
- 工具基础风险等级；
- 参数摘要：金额、数量等整数，令牌是否存在，姓名 / 备注是否存在，月份是否合法，未知参数数量；
- 本轮此前的工具调用名称与成功 / 拒绝状态；
- 服务端北京时间。

不传入用户原文、模型自由文本、账户姓名、收款人姓名、备注、手机号、卡号、令牌正文、密钥或历史聊天内容。参数中的字符串只以“是否存在”或严格格式校验后的值出现，避免把用户内容拼进护栏提示词。

`GUARD_SYSTEM_PROMPT` 明确要求结合 `local_time` 和 `previous_tools`：夜间/非日常时段的高风险准备动作、只读查询后立即切换目标、短时间连续高风险动作、重复准备/探测等，应标记可疑并触发风险升级；时间本身不是欺诈结论，只作为升级依据。

## 执行流程

1. 解析模型工具调用，校验参数为对象、无 `session` / `user_id`、敏感值未被直接传入。
2. 查找注册 Tool；未知工具仍由固定代码拒绝，不进入护栏。
3. 构造 `GuardCall` 摘要，调用 `GuardProvider.review()`；所有工具都经过该步骤。
4. `allow=true`：记录 `guard_allowed`，按工具基础风险继续。
5. `allow=false`：记录 `guard_denied`，不直接拒绝；标记本轮护栏升级，固定代码风险提升一档：绿→黄、黄→红密码、红密码→红密码+人脸。
6. 超时、Provider 异常、非 JSON、`allow` 不是布尔值或缺少字段：记录 `guard_failed`，同样按“提升一档”处理，最严为密码+人脸。
7. 只读工具没有副作用，护栏升级不会产生新的确认/验证界面，但仍记录审计；准备类工具会实际进入更严格流程。

## 配置与启用

- `GUARD_TIMEOUT_SECONDS`：护栏超时，默认 8 秒，范围 1～60 秒。
- 仅在配置了真实 `LLM_API_KEY` 时启用 `LLMGuard`；离线 Mock 不产生工具调用，因此不启用护栏。
- 护栏复用 `app/agent/llm.py` 的适配层，但使用全新的消息列表，不复用聊天历史，属于独立审查会话。
- 护栏模型输出只接受严格 JSON：`{"allow": true}` 或 `{"allow": false}`；其他内容一律拒绝。

## 审计

新增事件：

- `guard_allowed`：结果 `success`；
- `guard_denied`：结果 `denied`，固定原因 `guard_rejected`；
- `guard_failed`：结果 `failed`，固定原因 `guard_unavailable`。

审计不记录护栏输入摘要、模型输出原文或用户输入。拒绝后仍会记录原有 `tool_result` 失败事件。

## 已知限制

1. 离线 Mock 不启用护栏；真实模型下每次工具调用会增加一次模型请求和相应延迟。
2. 护栏是 LLM 判定，存在非确定性和误判可能；它只做风险升级，不再直接拒绝。固定代码的注册表、参数校验、风控、确认和事务边界仍是最终安全边界。
3. 红色风险分为“密码/验证码”和“密码+人脸”两级：大额转账为密码；挂失、理财申购/赎回/转换为密码+人脸；护栏升级可进一步提高。最严仅为密码+模拟人脸，未接入真实人脸识别。
3. 当前只审查单次工具调用与本轮历史，不做跨会话画像、频率统计或用户级熔断；后者属于 T-203。
4. 真实模型效果、超时阈值和对抗样本覆盖率仍需后续联调补充。
