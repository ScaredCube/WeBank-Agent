## 2. 产品与 UX 取舍

**核心判断**：在金融操作场景，“实时展示成功”与“刷新后依然有可信回执”必须一致；用户不应因为页面刷新而失去服务端成功凭据。

**与金融授权分离**：本轮只改变成功回执的**验证、存储与呈现**。内部转账的额度、是否即时执行、账户所有权及幂等保护仍归原有银行服务处理，模型无法自称成功来生成一张持久化回执。

**历史快照的时效**：其中的转账后余额为**执行当时的余额**，不是当前余额；刷新历史不会重新查询、扣款或修改既有交易。

**安全约束**：快照由服务端写入，严格 Pydantic 模型拒绝 pending、failed、无效金额、非人民币以及额外的 `confirmation_token`。使用已有加密 Vault，无密钥时保持既有报错边界，绝不回退为明文存储。

**备选方案**：只保留文本、要求用户跳转操作记录核实。虽然可用，但会割裂实时与历史体验。当前已有相应前端回执组件和加密快照基础，因此在原有结构中完成闭环是更小的增量。

## 3. 验证和边界

- 使用隔离 SQLite 的现有绿色内部转账端到端测试：服务端执行完成，SSE 展示 `operation_result`；历史 GET 还原同金额、同交易标识的回执，数据库快照加密、可重复读取。
- 使用同一个 `request_id` 重放已完成请求：不会再次执行扣款，回放不再下发原 `operation_result`，账户余额维持不变。
- 回执 Schema 反例：pending/confirmed/failed、非正金额、非法交易编号、非 CNY、额外确认令牌均被拒绝。
- 前端 `messageToolResults` 从历史 `tool_results` 还原 `internal_transfer`；无需改变用户界面布局。
- 本次未调用真实大模型决定转账，也不对正式银行或真实资金进行操作。

## 4. 回退

恢复 `27753f8` 的 `chat_turn.py`、`chat_messages.py` 和 `tool_results.py`，将行为基线回退到旧版。已落库的 `internal_transfer` 加密快照不会自动删除，但旧代码不显示该类别；恢复后的代码不会重新执行相关交易。回退前应结合正式历史快照兼容性审查。
