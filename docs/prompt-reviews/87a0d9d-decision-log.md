## 2. 附言 UX：不能靠一个必填/选填标志决定

目前事实（已从真实代码核对）：

- `backend/app/tools/transfer_tools.py`：`TransferArguments.note` 默认空字符串，并非 Tool 必需参数。
- `frontend/src/components/chat/ChatComposer.tsx`：前置意图激活时提示「补充金额和备注」，但未表达备注是否可选。
- `frontend/src/features/actions/PendingActionDialog.tsx`：会展示已有备注，没有发现直接编辑已准备操作备注的输入控件。
- 已准备操作具有明确的服务端参数/审计/确认边界；修改备注不能只在前端改显示值、继续使用旧确认令牌。

三种候选交互：

A. **强制追问备注**：适合特别需要备注的付款场景；增加轮次，可能反复要求用户回答非关键条件。

B. **默认空备注**（现行）：操作顺畅；新用户可能错过可选备注的存在。

C. **可发现但非阻塞的备注**（优先作为 UX 假设）：在编辑器明确标记「备注选填」，若用户已有附言则如实绑定；准备前可补充，进入确认后不允许静默更改。如需变更必须有可验证的重新准备流程。

**当前决定：未批准 A/B/C 为最终交互规范。** 先评估 UI 的可发现性、确认步骤和用户控制权；现行 B 保留于候选分支，不把它误报为已证实最佳 UX。

### 需要运行的差异场景

| 场景 | 需要检验的行为 |
|---|---|
| 已选账户/联系人/金额，未提备注 | 是否能快速继续，且看得到备注可选 |
| 已选所有条件，并提供备注 | 是否原样传递，确认页面是否准确 |
| 操作准备后试图补充或修改备注 | 是否阻止原确认令牌继续，提供安全的重新准备路径 |
| 用户说「不填备注」 | 不存入「无备注」等占位内容 |
| 用户已补充其他业务信息 | 不因附言重复询问付款人、联系人、金额 |

## 3. 两个更大的系统性风险（尚未改动）

**固定结果覆盖**：`agent/loop.py` 与 `tools/presentation.py` 在工具执行后常用确定性文本替代模型解释。这保护了可信金融数值，却可能遗漏分析与复合任务。建议建立「模型可解释但不可授权事实」的结果契约，进行设计评审后再修改 Runtime。

**Recovery 过度触发**：`response_policy.py` 的 `safe_action_clarification()` 对措辞、问号、开头词和长度都有严格限制；`AgentLoop` 因 `CLARIFY_ACTION` 可能额外调用恢复模型，增加延迟和模板感。后续应先统计真实调用频次、保留安全自然问句，再决定修改规则。

## 4. 质量证据与未验证项

既有证据：身份/Prompt 改动已通过 99 项相关测试；真实 DeepSeek 单轮问候出现自然的小We介绍；已选账户和联系人且未提备注时成功调用 `prepare_transfer`、返回 `action_required`（没有执行转账）。这只能证明当前模型的一次行为，无法证明长期体验或安全回归完整性。

未验证：多轮身份稳定、不重复广告语；用户能否发现和编辑选填备注；Guard 在新增绿级工具和异常工具的误拒/误放行率；复合查询回答质量。
