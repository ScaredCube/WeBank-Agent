# 小We · 跨账户周期性扣费识别与查询范围对齐

- **基线 Commit**：`9a8bbb8`
- **完整源码 Before / After**：[9a8bbb8-scope-alignment-review.md](9a8bbb8-scope-alignment-review.md)
- **范围**：订阅检测的账户维度，两个只读工具的服务端范围标记，以及复合查询的解释口径。
- **未修改**：System/Guard/Recovery Prompt、Tool Registry 的接口描述、ToolExecutor 授权与金融操作确认、转账备注 UX。

## Before / After

| 行为点 | Before | After |
|---|---|---|
| 订阅周期性检测 | 按 `(商户, 金额)` 将用户所有账户交易合并计数 | 按 `(账户, 商户, 金额)` 分组，只在同一账户内核验跨月份重复 |
| 两账户各发生一次相同商户同金额扣款 | 不同月份可能拼接为疑似周期性扣费 | 不会拼接为同一周期性候选；仍可识别单一账户跨月持续扣费 |
| 交易 Tool 的范围 | 结果没有明确范围元数据 | 成功结果包含服务端签发 `scope.kind=single_account`、`max_rows`（不包含账户 ID 或 Token） |
| 订阅检测 Tool 的范围 | 结果没有明确范围元数据 | 成功结果包含 `scope.kind=all_user_accounts` 和 `lookback_days=186`；检测仍覆盖该用户所有账户 |
| 两个 Tool 的复合总结 | 可能让用户把单账户最近交易与全账户近六个月检测线索误当同一个样本 | 明确两者范围不同，不允许把疑似订阅逐笔归因到本次交易列表 |
| 范围元数据不可用 | 无差异处理 | 回退为“无法核验两个查询的账户和时间范围是否一致”，不虚构匹配关系 |
| 检测窗口文字 | “近六个月” | “近186天”，对应实际滚动窗口 `6 × 31` 天 |

## UX / 风险判断

**对用户的收益**：更少假阳性、更清楚知道查询覆盖哪些数据，以及为何不能直接认定哪笔最近交易构成订阅扣费。这个改动优先保证信息可信度，暂不引入自动取消或新的资金操作。

**为什么不直接合并两套 Tool 的交易记录？** 最近交易仅从一个账户取前 N 条；订阅检测扫描用户所有账户的近 186 天支出。这两个数据集的来源、窗口和去重粒度不同。直接做关联将产生难以证明的结论，必须先实现可核验的账户与交易引用关系。

**限制**：当前候选检测基于同账户、同商户、同金额且跨月份发生，并不代表自动续费协议成立，也不意味着发生了重复订阅；同一商户同金额但属于不同合同的行为不能仅凭流水识别。增加范围标记只用于模型解释，不代表数据被授权从账户间合并操作。

**数据保护**：`scope` 只有枚举类型、条数上限和天数，不暴露真实账户 ID、Token 或完整卡号。真实账户归属仍由服务端查询和 `ToolExecutor` 验证。

## 测试与验收

- `test_scope_alignment.py`：两账户跨月假阳性被拦截；单账户跨月真候选保留；服务端范围标记正确且不含 ID / Token；不完整或错误范围标记必须回退。
- `test_compound_read_summary.py`：完整 Chat 链路输出包含真实范围，不将只读结果推断为已取消订阅；用户明确不要求订阅检测时不额外提示。
- 结合订阅、账户、Runtime、Prompt 版本测试做定向回归。
- 实际供应商测试使用隔离 SQLite 和临时测试密钥，不对真实账户或订阅执行操作；仅能说明该场景一次观察，不能代替跨模型、跨账户全面验收。

**回退**：恢复基线 `subscription_service.py` 的分组、两种 Tool 的 `scope` 输出及复合摘要相应段落；重新生成行为版本基线并运行相关测试，无需修改正式 DB 或 Prompt。
