# 小We · 明确双目标只读任务的单次补齐机制

- **基线 Commit**：`2eb7454`
- **完整自动代码 Before / After**：[2eb7454-read-goal-continuation-review.md](2eb7454-read-goal-continuation-review.md)
- **System Prompt / Guard / Recovery 原文**：本轮没有修改。
- **变更对象**：`agent/compound_read_summary.py` 的遗漏目标识别、`agent/loop.py` 的受限补齐流程；其中追加了一条**服务端创建的临时 system 角色提醒**，属于生效模型指令，必须和 Prompt 一样审查。
- **权限**：ToolExecutor、Guard、账户所有权、金融操作确认及执行方式均未修改。自动补齐只允许一个尚未调用过的只读工具，模型不能利用它执行新的写操作。

## 1. Before / After（相同输入）

用户输入：「查询最近交易流水，并检查是否有重复订阅」

| 场景 | Before | After |
|---|---|---|
| 模型先调用 `list_recent_transactions`，随后输出“两个目标都完成了”，未调用 `detect_subscriptions` | Runtime 直接结束，返回可信交易以及“订阅识别尚未完成”，用户须再次提问 | 服务端从本轮用户原始请求与可信工具轨迹发现遗漏，给模型**一次**补齐机会；如模型正确调用 `detect_subscriptions`，可在本轮完成两个目标 |
| 模型补齐后再次声称取消订阅成功 | 原有工具可信性保护 | 仍只展示可信结果；不接受虚构的取消订阅或转账成功 |
| 模型忽略补齐提醒 | 直接结束 | 最多补一次；最终诚实说明订阅识别仍未完成 |
| 模型收到补齐提醒后试图调用 `prepare_transfer` 等其他工具 | 旧版没有该补齐步骤 | **拒绝执行无关 Tool**，以已验证结果生成部分完成回复 |
| 某个只读工具已被调用但返回失败 | 原有路径 | 不对已失败工具做额外自动重试，避免超时与无效循环 |
| 用户只查交易，明确不需要订阅 | 原有正常查询 | 保持正常路径，不增加另一项查询和延迟 |
| 双目标均已成功调用 | 原有可信完整结果 | 保持原有执行路径，不发生额外模型请求 |

**具体变化**：只有首个只读结果成功且确实只有一个目标已经尝试时，才检查是否有一个未执行的明确只读目标。它不是新的通用任务规划器，也不意味着“每个多目标请求都自动补齐”。

## 2. 追加给模型的系统级指令 — Before / After

**Before：** 没有这一步内部提示；若模型停止调用 Tool，则直接进入最终回答分支。

**After：** 仅在满足上方严格条件、模型已提前停止时，临时追加如下内容；其中工具名由服务器确认的缺失目标填入（只能为 `list_recent_transactions` 或 `detect_subscriptions`）：

> 服务端只读任务覆盖检查：用户明确请求最近交易查询和疑似订阅识别。已有可信结果只覆盖其中一项，尚未尝试的工具为 {missing_goal}。如有足够条件，请优先调用这个只读工具完成剩余目标。遵守现有权限与账户范围，不得执行写操作、不得重复已成功的查询。如无法查询或需要用户选择账户，请正常解释尚未完成的目标。不得把疑似周期扣费直接断言成重复订阅。

这段文本来源于**服务端可信结果和有限枚举工具**，没有拼接任意用户文本或模型输出。实际金融授权仍由独立程序执行，不能仅依赖本指令。

## 3. UX 取舍与控制边界

**收益**：用户明确提出两项目标时，模型不必因中途遗漏而强迫用户再次发起相同请求。更贴近「小We · We在你身边」的持续服务能力。

**成本**：遗漏时增加一次补齐决策的模型推理；如果模型随后成功调用第二个 Tool，通常还需一次最终回答推理（相较旧版最多增加两次模型请求）。已完整完成时没有额外消耗。

**限制**：目前只支持「最近交易 + 疑似订阅」这组有清晰 Tool 对应关系的只读任务；更复杂的复合任务仍由原模型循环与可信结果策略处理。未来是否推广，需要先有可审计的目标识别方法，不能简单往主 Prompt 添加“全部任务必须完成”的强制条款。

**避免错误覆盖**：不能因为请求里出现“订阅”两个字，就认为用户要检查订阅；明确说“不需要、下次再说、暂不”等必须跳过。混有取消、转账、支付等操作意图的请求不自动补齐。

**输出边界**：无论模型是否配合补齐，只有实际执行成功且结构可信的 Tool 结果能证明该目标已完成；疑似周期性扣费仍不等于确认重复订阅。

## 4. 验证与残余问题

- 固定 Fake LLM 端到端测试：模型第一轮执行交易查询，第二轮提前回答，第三轮被提醒后调用订阅检测，第四轮完成；最终文本来自可信工具，不包含模型虚构的资金操作成功。
- 上限测试：模型第二轮停止、第三轮仍不调用工具时只会再请求一次，返回明确的部分完成摘要。
- 反例：用户拒绝订阅检查、混有写操作、重复或失败工具、伪造转账工具调用，都不会触发越权操作。
- 与账单、Guard、ToolExecutor、Prompt 版本基线相关测试共同执行；保留定向而非无差别全量回归。
- **真实 DeepSeek 复验**：一次交易 + 订阅场景真实调用两个只读工具并正确返回结果；由于模型原本就完成两个目标，这次没有实际触发新增的补齐提醒。因此“补齐分支”的真实模型效果尚须更多观察，不以一次结果宣称已验证全部路径。
- **回退**：移除本次 Loop 补齐分支与遗漏目标识别，更新版本基线，复测相同场景；无需变更正式数据、密钥、Prompt 主文或金融执行权限。
