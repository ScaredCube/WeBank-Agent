## Before / After：相同任务的实际输出行为

用户请求：「请查询最近的交易记录，并识别可能的重复订阅」。

**Before**

当模型正确调用 `list_recent_transactions` 与 `detect_subscriptions`，Runtime 仍将两份结果直接拼接（或对某个单独结果渲染）。例如：

> 模拟交易记录：……（交易列表）
>
> 未从最近模拟流水中识别到可能的重复订阅。

这一表述没有解释检测器实际只识别“跨月份相同商户、相同金额”的周期性扣费候选，也没有明确区分候选订阅和重复订阅。模型若提前停止且只调用一个工具，旧版也没有明确说明另一个用户目标尚未完成。

**After**

当两个可信结果均返回时，先生成有限结论，后附经服务端渲染的交易和疑似扣费明细。例如，在相同固定样本中：

> 最近交易查询本次返回 2 笔记录。从近六个月的支出流水中识别到 1 项疑似周期性扣费线索。同一商户、同一金额跨月份出现，只能提示可能的订阅扣费；不能单凭这些记录认定存在重复订阅或异常扣费。建议对照订阅清单及扣费日期核实。
>
> 模拟交易记录：……（可信 Tool 明细）
>
> 可能存在的订阅：……（可信 Tool 明细）

当只完成交易查询时：

> 最近交易查询本次返回 1 笔记录。本轮尚未完成可核验的周期性扣费识别。……（风险边界说明与已查到的交易明细）

金额、商户、账户等个人金融数据仍只由可信 Tool 的既有展示逻辑提供；新增文字只引用 Tool 行数和已验证的查询覆盖情况，不引入模型自行推测的资金数字。

## 产品与 UX 判断

1. **多目标完成度可见**：用户能区分“查到了交易”与“识别过订阅线索”，避免因模型自由陈述而误以为两项任务都完成。
2. **候选与事实分离**：检测器从大约六个月的支出流水里筛选跨月份同商户同金额的记录；这是周期性扣费候选，不能证明双重订阅、重复支付、合同状态或诈骗。
3. **具体结果保留**：不会为了简短总结而隐藏原本存在的交易明细。
4. **局部且保守**：仅处理这两个只读工具的组合；单独交易查询、混合账单/其他工具仍走既有逻辑。识别到用户明确「不要检查订阅」时，不擅自提示订阅任务未完成。
5. **未执行任何动作**：即使用户在同一请求中提到取消订阅，这两个只读工具也只能查询与识别；答复必须明确取消并未执行。

**局限与下一步**：完成度识别仍是保守的局部规则，不是通用多目标规划器；返回“检测完成”不等于“确认重复订阅成立”。`detect_subscriptions` 的检测范围可能涉及用户多个模拟账户，而 `list_recent_transactions` 是单账户近期记录，不能据此断定两个数据集是完全相同的样本。未来如果要交叉分析异常扣费，需要引入来源范围与时间窗口的一致性核验。

## 安全对照与测试

| 相同输入的场景 | Before | After |
|---|---|---|
| 两个只读 Tool 均成功，检测到候选 | 原始结果并列展示 | 先给查询覆盖和候选性质的有据总结，明细保留 |
| 只完成交易查询，模型谎称订阅排查完成 | 只输出交易明细，未明确未完成的目标 | 说明订阅识别尚未完成，不采纳模型自述 |
| 两个工具成功，但模型谎称扣款金额与已取消订阅 | 原始 Tool 文本覆盖模型文本 | 继续使用可信 Tool，不采纳虚构金额及取消状态 |
| 没有识别到周期性候选 | 原文可能让用户理解成“没有重复订阅” | 明确为“本轮未识别到线索”，不推出“不存在重复订阅” |
| 用户明确只查交易、无需检查订阅 | 正常返回交易数据 | 保留正常路径，不增加不必要的未完成提醒 |

自动化验证包括单元级 Tool 证据检查、Fake LLM 的完整 Chat API 流程、缺失第二个工具的反例，以及原有 Runtime、ToolExecutor 等定向回归。

**真实模型复验（一次）**：`deepseek-v4.1-flash-1017` 经 Tokendance，在隔离临时 SQLite 与临时测试密钥环境中，确实调用 `list_recent_transactions`、`detect_subscriptions`，最终显示本次 3 笔交易、没有检测到近六个月周期性候选，并保留交易明细。无任何 `action_required` 或执行操作。此为单个场景观测，不代表整套 Agent 的可靠性已全面验证。

**回退**：恢复 Loop 的原输出分支并移除 `compound_read_summary.py` 与对应登记，重新生成版本基线；无需更改数据库内容、Tool 权限或生产 Prompt。
