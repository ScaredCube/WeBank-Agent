### Guard Prompt 的局部修改与依据

主线提示中出现：
- “时间与历史调用明显不连续……短时间内连续切换目标”；
- “先只读查询再异常切换收款人、来源账户或产品，且参数摘要显示目标发生变化”；
- “短时间内连续出现多个高风险动作”。

但当前 `GuardCall.to_payload()` 只提供 `local_time`（**本次**）、`previous_tools`（工具名及成功/拒绝结果）和**本次**参数形状摘要；没有各轮时间戳、历史目标或历史参数。因此不能有证据地判断“短时间内”“目标变化”。我们将其改写为：
- **本次时间**可用于评估时段风险；没有历史调用时间戳，不推断调用间隔；
- **历史工具**只能证明本轮有哪些工具成功/失败；先只读再准备本身不构成异常，不能声称历史目标变化；
- 允许根据确实可见的重复调用、多次被拒绝、当前字段异常作出上调判断。

主线的“不把 Guard 变成全拒绝”、对夜间高警惕和风险升级幅度均保留。该修改改变 Guard 的模型判断依据，**不改变程序允许调用的工具范围、实际金融权限或业务阈值**。

### 风险和不变量

- 主线将 Guard 的 deny 和 unavailable 都改为风险提升。这有利于减少模型保守误拒，但会让原本 hard-deny 的准备请求进入额外模拟验证；**作为产品政策应由金融业务负责人正式签收**，不能把当前比赛模拟 OTP/Face 当成真实银行强验证。
- `validate_tool_arguments`、敏感号码拒绝、用户选中账户服务端重新绑定、ToolExecutor 二次身份校验、确认令牌不得进模型输出等不变量保持。
- contextvar 必须只在准备工具实际 Handler 范围置位、无论异常成功都在 `finally` 恢复；避免前后请求风险污染。
- 新 UI 与旧端到端脚本的差异应修复测试，不应倒改真实页面的惰性会话逻辑。
