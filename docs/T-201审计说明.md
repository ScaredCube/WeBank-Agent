# T-201 持久化审计

## 查询与关联

`GET /api/audit?after_id=0&limit=100` 使用登录令牌，只返回当前用户的记录，按 `id` 正序；`limit` 为 1–500，继续读取时将最后一条 `id` 作为 `after_id`。响应为数组，包含 `id`、`user_id`、服务端生成的 `request_id`、可空 `conversation_id` / `action_id` / `transfer_id` / `transaction_id`、`event_type`、可空 `tool` / `risk_level` / `reason_codes` / `result` 及 `created_at`。响应禁止缓存。

对话事件通过服务端会话上下文和请求 ID 关联；之后的确认、验证和执行使用归属当前用户的动作 / 转账，找到先前记录的真实会话。直接 REST 发起没有会话，`conversation_id` 为 null；不存在或不属于该用户的 ID 不会附到该用户日志。不同 HTTP 请求各有新的 `request_id`。工具调用与准备通过同一请求 ID 关联；动作与转账 ID 连接后续请求。

## 事件与事务

- `tool_called` / `tool_result`：Agent 工具调用；查询工具记录结果和绿色判级，执行异常时记录固定失败代码，不记录异常原文。
- `risk_assessed`：`risk_level` 为 green / yellow / red；原因代码为 `base`、`confirmation_required`、`daily_limit`、`night_upgrade`。拒绝的风险升级单独持久化。
- `transfer_prepared`、`transfer_prepare_retried`、`transfer_prepare_denied`、`transfer_prepare_failed`；`action_confirmed` / `action_confirm_denied`、`action_cancelled` / `action_cancel_denied`。
- `verification_started`、`verification_succeeded`、`verification_failed`、`verification_locked`、`verification_denied`、`verification_start_denied`、`verification_start_failed`、`verification_error`。
- `transfer_completed`、`transfer_retried`、`transfer_denied`、`transfer_failed`。完成仅记录一次；重试是独立事件且指向原交易，不代表再次扣款。拒绝原因使用固定代码，例如 `not_authorized`、`insufficient_balance`、`risk_upgrade`。

成功转账、流水、余额与 `transfer_completed` 在同一 SQLite 事务中提交；审计写入失败会中止并回滚，不报告成功。准备、确认、取消和验证的状态变化与其审计记录同事务。业务拒绝或异常在原事务结束回滚后用独立事务记录；如果审计数据库本身不可用，该记录也可能无法保存，此时请求失败，不能声称完成了审计。现有 SQLite 转账限制不变。

审计只接受固定事件、工具名、状态和原因代码，不保存自由文本、用户输入或摘要、模型上下文、请求体、工具参数、交易金额、姓名、手机号、卡号、备注、密码、验证码、确认令牌、JWT、密钥或密文。未知工具名记为空。审计保护范围不等于全系统隐私保护：目前聊天消息及模型输入仍未做 T-207 入站脱敏。

## T-207 事件预留

事件名 `token_resolved`、`token_resolve_denied`、`token_revoked` 已保留在事件白名单，但目前没有调用方、Vault 或真实事件。后续实现需另行确定并校验数据引用标识、实体类型 / ID、拒绝原因及用户归属的专用白名单字段；禁止把一次性确认令牌、明文、密文或密钥写入。当前 AuditLog 尚无这些 T-207 专用字段，不能称为 T-207 已实现。
