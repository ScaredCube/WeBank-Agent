## 1. 项目概况

本项目为“银行 AI 智能体”参赛作品，目标是让用户用自然语言完成银行服务：Agent 负责理解意图与组织流程，所有真实业务动作由后端固定代码执行，并对 AI 保持零信任。

当前版本是演示骨架：登录、会话持久化和模型适配可用；模拟账户查询和模拟转账已接入后端及 Agent。转账确认尚未接入前端，真实银行、账单分析、卡片、理财、完整审计和护栏尚未实现。

## 3. 系统架构

```
浏览器
  │  React 19 + Vite（登录 / 对话 / 确认弹窗）
  │  fetch + SSE 解析
  ▼
Vite dev proxy  /api ──────────────► FastAPI
                                       │
                        ┌──────────────┼───────────────┐
                        ▼              ▼               ▼
                   api/routes     agent/loop       db/services
                   auth/chat      LLM adapter      SQLModel + SQLite
                        │              │
                        │              ├─ MockProvider（离线）
                        │              └─ OpenAIProvider（OpenAI 兼容）
                        ▼
                  services/chat_service（会话与消息事务）
```

设计边界：

- 路由只做鉴权、参数校验与编排，不直接调用模型客户端。
- 所有模型调用经过 `backend/app/agent/llm.py`。
- AgentLoop 注册绿色只读 Tool 和黄色模拟转账准备 Tool；按服务端登录用户执行，不信任模型提供的用户 ID。
- 工具执行循环有次数限制；Agent 只产生待确认或待模拟验证动作，不直接扣款。

### 4.4 账户与交易只读工具（T-101，进行中）

- 新增模拟 `Account` 和 `Transaction` 表，金额以整数分存储；启动时为演示用户幂等创建一个账户和三条模拟流水。
- `account_service` 按用户隔离账户和交易查询；交易按时间倒序，默认 10 条、最多 50 条。
- `app/tools/` 提供余额与最近交易查询、参数校验、统一结果和绿色风险元数据；执行日志仅为占位，不是持久化审计。
- AgentLoop 已向兼容模型提供工具定义并执行调用，模拟模型测试覆盖了余额查询与拒绝伪造用户 ID；离线 Mock 不调用工具。
- 工具调用后的余额和交易查询结果由固定代码根据 Tool 返回值格式化；没有工具调用时显示固定提示，不显示模型自由文本，以免编造银行信息。Tokendance 余额查询已用隔离临时数据库验证，前后端完整对话尚未验证。每轮模型输出目前先缓冲再发送，实时流式体验暂受影响。

### 4.5 固定代码风控（T-102，进行中）

- `app/risk/engine.py` 根据服务端工具元数据和可信上下文判定风险，现有只读 Tool 执行前经过判定；黄 / 红工具暂不执行。
- 转账规则以整数分计算：本次金额加当天已完成累计不超过 1000 元为黄，超过为红；判定不会降低基础风险。累计数据由服务端查询当天已完成模拟转账，不信任模型传入的累计值。
- 演示夜间按北京时间 00:00–06:00 将黄色升级为红色；`RISK_NIGHT_START_HOUR` 和 `RISK_NIGHT_END_HOUR` 可配置起止整点，启动时校验，绿色查询不因夜间自动升级。具体时段待业务确认。
- Tool 执行前的风险判定通过日志记录工具、用户 ID、等级及规则原因，不记录工具参数或账户数据；该日志不等于持久化审计。
- 模拟转账后端已接入可信累计查询、黄色确认和仅限调试的红色模拟验证；真实验证及前端接线尚未实现。

### 4.6 服务端确认（T-103，进行中）

- 内部服务仅为黄色风险动作创建待确认记录，并生成随机一次性令牌；数据库保存令牌哈希，不保存令牌明文。
- 确认时校验用户、令牌、黄色风险、待确认状态和有效期；原子更新防止重复或并发确认。默认有效期为 300 秒。
- 详情查询只允许所属用户访问，不返回令牌哈希且设置 `Cache-Control: no-store`；过期但未处理的动作展示为 `expired`，不修改数据库状态。
- 取消仅允许所属用户操作未过期的待确认动作；取消与确认并发时最多一个成功。
- 模拟转账准备接口和 Agent Tool 会创建动作并首次返回令牌；确认成功仅记录确认，需独立调用执行接口。前端尚未接线。

### 4.7 模拟小额转账（T-104，进行中）

- `POST /api/transfers/prepare` 根据登录用户、账户余额、金额和服务端日累计判断风险；黄色动作等待确认，红色动作仅在 `DEBUG=true` 下允许创建并等待模拟验证，`DEBUG=false` 时拒绝红色操作。
- `POST /api/actions/{id}/confirm` 只记录确认；`POST /api/transfers/{id}/execute` 再次验证确认有效期、余额及风险，在 SQLite `BEGIN IMMEDIATE` 事务中扣款并生成交易记录。
- 同用户幂等键唯一；重复准备不会返回令牌明文，重复执行返回原流水。并发不同转账在锁内重新计算累计，防止绕过日累计限额。
- 收款人是模拟外部对象，不连接真实银行或真实收款账户。手机号仅保存脱敏值和基于服务端 JWT 密钥的 HMAC，不写入流水；令牌丢失后无法恢复，需取消或等待过期并使用新幂等键。
- Agent 的 `prepare_transfer` Tool 只创建待确认动作；`action_required` 事件把令牌直接交给客户端，令牌不返回模型或写入会话历史。测试覆盖伪造用户 ID、模型伪造成功和聊天文本“确认”不能扣款。
- 仅支持 SQLite，尚未接入前端、真实多因素验证或完整审计；更换 JWT 密钥会影响旧请求的手机号幂等匹配。当前前端忽略确认事件，令牌只发送一次，断线或未接线可能导致无法恢复，只能等待动作过期。

### 4.8 模拟强验证基础（T-105，进行中）

- 仅 `DEBUG=true` 时可为红色模拟转账启动验证，依靠登录用户、动作和一次性令牌绑定；固定测试码通过 `DEMO_VERIFICATION_CODE` 配置，默认 `123456`，绝不是实际短信或生产多因素验证。
- 每个动作最多一个验证会话；重复启动不会重置失败次数，验证码三次错误锁定，有效期不超过动作有效期和 5 分钟。SQLite 写锁保证并发检查与失败次数更新原子性。
- 仅存验证码 HMAC 摘要，不存或记录明文；成功后状态变为 `verified`，不会执行动作。黄色确认接口不能处理红色动作，取消或过期后验证不可用。
- `DEBUG=false` 禁用整个模拟验证流程并拒绝红色模拟转账。`DEBUG=true` 时验证成功后可独立调用执行接口，执行时重新检查动作与验证有效期、余额及风险；红色动作不会降级为只需普通确认。前端和真实短信尚未接入，失败锁定目前按动作而非用户累计。

## 5. 接口清单

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/health` | 否 | 健康检查，返回 LLM 模式与模型名 |
| POST | `/api/auth/login` | 否 | 登录，返回 JWT 与用户信息 |
| GET | `/api/auth/me` | 是 | 当前用户 |
| GET | `/api/auth/demo-account` | 否 | 仅 debug 下返回演示账号 |
| GET | `/api/actions/{id}` | 是 | 查询所属动作详情与当前状态，不返回令牌 |
| POST | `/api/actions/{id}/confirm` | 是 | 验证一次性令牌并记录确认，不执行交易 |
| POST | `/api/actions/{id}/cancel` | 是 | 取消所属的未过期待确认动作 |
| POST | `/api/actions/{id}/verification/start` | 是 | 为红色模拟动作启动模拟验证 |
| POST | `/api/actions/{id}/verification/verify` | 是 | 校验模拟验证码，不执行操作 |
| POST | `/api/transfers/prepare` | 是 | 创建模拟转账及待确认动作，首次返回一次性令牌 |
| POST | `/api/transfers/{id}/execute` | 是 | 已确认动作经二次风控后执行模拟扣款并记流水 |
| GET | `/api/chat/conversations` | 是 | 当前用户会话列表（按更新时间倒序） |
| POST | `/api/chat/conversations` | 是 | 新建会话 |
| GET | `/api/chat/conversations/{id}/messages` | 是 | 会话历史消息 |
| POST | `/api/chat/conversations/{id}/messages` | 是 | 发送消息，SSE 返回 |

SSE 事件格式（`data` 为 JSON）：

```json
{"type": "delta", "text": "..."}
{"type": "done", "message": {"id": 1, "role": "assistant", "content": "..."}}
{"type": "error", "message": "中文错误提示"}
{"type": "action_required", "tool_calls": [], "action": {"id": 1}, "transfer_id": 1, "confirmation_token": "<一次性令牌>"}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | int, PK | 自增主键 |

| role | str | user / assistant（system 预留） |
| content | str | 消息正文 |
| created_at | datetime | UTC |

> 数据库无迁移工具，表结构变更目前依赖删除 SQLite 文件重建。

### Account 与 Transaction（模拟）

- `Account`：`id`、`user_id`、`name`、`masked_number`、`currency`、`balance_fen`、`status`、创建 / 更新时间。
- `Transaction`：`id`、`account_id`、唯一 `reference`、`direction`、`amount_fen`、`balance_after_fen`、`counterparty`、`category`、`note`、`occurred_at`。
- 金额单位为分；账户归属由查询服务根据服务端用户 ID 校验。

### PendingAction

- `id`、`user_id`、`action_type`、`details_json`、`risk_level`、`status`、`token_hash`、`created_at`、`expires_at`、`confirmed_at`。
- 令牌明文仅在模拟转账首次准备时通过 API / SSE 返回给客户端；动作详情不返回令牌，也未通过前端展示动作。

### TransferRequest（模拟）

- `id`、`user_id`、`account_id`、`action_id`、`idempotency_key`、`recipient_name`、`recipient_phone_masked`、`recipient_phone_digest`、`amount_fen`、`note`、`status`、`transaction_id`、`created_at`、`completed_at`。
- 每个用户的幂等键唯一；`completed_at` 用于计算北京时间当日已完成转账累计。

### VerificationSession（仅演示）

- `id`、`action_id`、`user_id`、`code_digest`、`attempts`、`status`、`created_at`、`expires_at`、`verified_at`；每个动作最多一个会话，验证码明文不入库。

## 7. 安全设计现状

已落地：

- AI 不接触银行业务 API；只读模拟 Tool 经服务端执行并按当前用户隔离。
- JWT 鉴权，会话与消息接口均校验归属关系。
- 密码使用 Argon2 哈希，错误提示不区分账号不存在与密码错误。
- 系统提示词明确禁止编造账户、交易与金额，并拒绝越权请求。
- 前端确认弹窗为固定组件，AI 无法生成或绕过。
- 密钥、数据库、构建产物已加入 `.gitignore`。

仅有骨架、尚未落地：

- 模拟转账的前端接线、真实多因素验证及按用户累计失败的熔断机制。
- 审计日志与决策链路追踪。
- 独立会话子 Agent 的调用前安全检查。
- 异常熔断、限流、注入防御。
- 受限计算工具。
- 工具级事务与回滚。

## 9. 已知限制与风险

1. **业务能力有限**：模拟余额、交易和转账准备已接入 AgentLoop；模拟转账尚未接入前端或真实银行。账单分析、卡片、理财、订阅未实现。
2. **对话体验受限**：Mock 不调用工具；无工具调用时仅显示固定提示，模型自由文本暂不展示；模型回复按轮缓冲，不再实时逐字显示。
3. **确认弹窗尚未接后端**：前端仍是本地演示；后端已将确认机制接入模拟转账，确认与执行分开，尚无前端令牌交付体验。
4. **无审计与熔断**：关键操作不可追溯，安全自评报告所需证据尚不完整。
5. **单用户体系**：仅演示账号；JWT 无刷新与吊销机制，token 存于 localStorage。
6. **会话管理粗糙**：新建会话立即入库，空会话会累积；无删除、重命名、分页。
7. **无数据库迁移**：模型变更需手动删库重建。
8. **SQLite 并发能力有限**：开发配置 `check_same_thread=False`，不适合生产。
9. **前端包体**：主 chunk 约 512 kB，后续可按路由拆分。
10. **未部署**：无 Docker、无生产环境变量加固、无 HTTPS / 反向代理配置。
