**评估时点**：2026-11-02；**目标分支**：`klutz-runtime`；**主线来源**：`origin/main@602a4e8`；**集成前分支**：`730e8c8`。

## 核心判断：分两层交付

1. **可控访问的比赛演示 Web**：适合作为近期唯一上线目标。只连接合成银行数据，单节点运行 FastAPI + SQLite 持久存储，构建后的 Vite 静态文件与 API/SSE 统一走 HTTPS 反向代理。严格限制访问者/共享测试账号，标记“模拟业务”。通过下述 P0 门禁后可部署测试预览；单次 E2E 通过不等于已完成部署。
2. **公开多用户金融服务、接入真实账户或真实资金**：**现阶段不具备上线条件**。当前银行账户、风控验证、身份模型及存储均围绕比赛模拟设计；需要独立的金融安全、合规和持久化体系，不能把第一层成功等同于第二层。

## 本次 main 集成影响

- 主线新增：左右资产/工具侧栏，手机资产入口，Motion 动效，聊天消息和资产交互调整；原“新对话立即创建”改成**发送时惰性创建**。保留两侧功能和本分支已有的 Agent、可信结果、异常恢复、浏览器工具链。
- 主线扩展了代码风控：Guard 的 `allow:false` 提升固定风险一档而非无条件取消操作；新 `password_face` 模拟双因子验证。原分支 `ToolExecutor` 是实际执行边界，已在其中接入风险升级并用 `try/finally` 重置 ContextVar，未退回主线旧版重复执行器。
- 主线修改了 Guard System Prompt。对其增量明确了实际服务端证据边界：Guard 只能看到**本次时间、当前参数摘要、历史工具名/结果**，不能凭空判断历史目标变化、各次调用时间间隔或跨会话异常频率。保留主线“有具体异常依据才上调风险”的设计，避免模型制造虚假风险证据。其余主身份 Prompt、Recovery Prompt 保留现有内容。
- 主要跨端适配：合成转账 E2E 移除旧版的“点击新对话会立刻 POST”的错误预期，在新版惰性建会话时通过第一条消息创建。继续核验真实工具、确认、执行与审计，不绕过服务端。
- 版本审查：`docs/prompt-reviews/730e8c8-main-602a4e8-merge-review.md`；人工安全决策：`docs/prompt-reviews/730e8c8-main-integration-decision.md`。

## P1 · 首次演示之后可迭代

- 生产前端 chunk 有超 500 kB 的构建告警；可在演示后做路由级代码拆分与性能预算。
- 真实 DeepSeek 选择 Tool、Guard 时间敏感性及复合意图需要多样本稳定性观察；单次成功不应推断普遍可靠。
- 多用户隔离、账户体系、跨设备收藏、跨地域高并发、PostgreSQL 迁移、生产可观测性与 CI/PR 门禁应作为下一阶段工程项目。
- UI 动效需手机真机与低性能设备抽样验证，`prefers-reduced-motion` 已有实现和对应前端测试。

## 推荐执行顺序

**先冻结这次 main 集成 + 完成测试与安全审查 → 配置独立演示部署环境（密钥、SQLite 持久卷、HTTPS、SSE） → 演示环境自动/人工冒烟 → 小范围可控预览 → 再考虑公开访问与更长期的基础设施改造。**

第一层以稳定可演示为先；不把真实金融生产安全未就绪的问题伪装成少量 UI 调整就能解决。

## 合并后的额外真实模型验收发现

- 本轮 **确定性 Chrome/Agent/SQLite 模拟转账 PASS**；现有浏览器操作 E2E 的确认流程仍默认黄色确认。
- 合并后另一次 **真实 DeepSeek 模拟转账 E2E 未通过**：日志显示先有 Guard 拒绝及参数/引用问题，随后服务端已创建一笔可信待处理转账，但 UI E2E 未完成执行。本次不计作成功，也没有真实资金移动。Guard 风险升级可能要求红色模拟验证，需要单独复核浏览器验证链路及执行审计；不得为了提升通过率关闭 Guard 或自动通过验证码。
- 因此“可控比赛演示部署”尚需要**合并后真实模型对黄色/红色不同风险路径的最终验收**。在此之前，现有测试绿灯只证明代码和确定性主链路，不证明真实模型在新 Guard 下稳定完成全部任务。
