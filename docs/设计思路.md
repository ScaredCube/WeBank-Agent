## 安全性&可靠性

### 工具层模块化

核心业务用Tools（例如智能转账、查账单、卡片挂失、理财申购等），增加安全性，也可以保证数据库事务一致。

外部生态联动用MCP（例如生日前订鲜花/蛋糕、查实时汇率等），增强拓展性

使用银行原本的工具设计，该输密码的还是要输密码。该Agent仅作为简化操作流程

### 风控等级

首先是功能本身的风险等级：

| 级别 | 执行策略 | 典型操作范围                                                 |
| ---- | -------- | ------------------------------------------------------------ |
| 绿色 | 自动执行 | 余额查询、交易记录查询、账单分析、理财收益查询等纯查询类操作，Agent 确认意图后直接执行，无需二次确认 |
| 黄色 | 用户确认 | 小额转账（日累计 ≤ 1000 元）、订阅查询 取消、虚拟卡申请等，执行前展示操作详情并获得明确确认 |
| 红色 | 强验证   | 大额转账（日累计 > 1000 元）、密码修改、卡片挂失 解挂、理财产品申购等，须通过人脸识别、短信验证码或 U 盾等多因子认证 |

用户确认和验证都是功能侧硬性弹窗，而不是由LLM确认。确认窗口不用Generative UI画，给AI发“确认”信息也无效。

强验证可以再划分为密码验证或人脸识别

然后是外部环境的风控因素：

比如操作时间、定位、IP置信度、系统状态、转账对方的信息等等。例如白天小额转账为黄色等级，半夜则为红色。

### AI安全护栏（类似子Agent）

每次调用工具时都使用独立会话的子Agent进行检查。类似Claude Code的自动模式会检查指令安全性的设计

不给这个子Agent传用户输入的提示词，只看调用行为（包含此次调用的功能和调用理由，以及历史工具调用记录和调用时间），如果有风险就拦截。

可以给这个子Agent传一些外部环境风控因素之类的

### 防计算幻觉

避免让LLM口算数字产生幻觉，做一套只能用于计算的外部工具（简化版的python？或者自创一套简单的计算语言？）

不要搞成完整的代码运行环境，不给计算之外的权限

Gemini给出的建议是基于 Python `ast` 的纯数学表达式求值器 + `simpleeval` 库，感觉还行

### 敏感数据替换

在AI交互层面不传输敏感信息（例如银行卡号、手机号），用占位符代替，直到传输给原生工具之后才会被替换成具体卡号。AI看不到敏感信息。

相应的，可能要维护一套键值对应的信息库，作为全局记忆的一部分。最好可以加密一下

也可以防止AI幻觉抄错银行卡号

### DAG长期任务（这部分还没完全想好）

类OpenClaw的设计

支持模糊表达、省略上下文、隐含意图的识别；复杂任务需拆解为有序的子任务 DAG（有向无环图）；执行过程中支持中断、回退和人工接管。

自研轻量 DAG 状态机，不用LangChain。便于严格控制上下文和提示词传入，保证安全性和可控性。DAG的每个节点都是一个子任务，子任务之间有依赖关系，执行顺序由DAG决定。

### 负一屏拖拽式卡片

主屏是一个比较传统的AI对话界面

左划负一屏可以做三个抽屉，展示银行卡（卡别称，尾号和余额）、常用联系人、理财持仓（产品名，持仓，昨日收益）。

抽屉里的元素可以拖动交互，比如把 银行卡1 拖到 联系人A 上就是用卡1给A转账，卡2拖到卡1上就是用卡2给卡1转账，基金甲拖到卡1上就是赎回到卡1，卡1拖到基金上就是增加买入 等等

拖拽交互后跳回主屏AI界面，附在用户提示词前，便于AI理解前置意图。这样的话就不用和AI完整说“用卡1给A转账1000元”，只需要说更详细的指令 “1000元，饭钱” 即可完成转账备注和转账金额的填写

卡片也可作为基础信息展示。毕竟很多时候用银行APP只是想查余额，还要和AI说“卡1还有多少钱”实在有点蠢。全局小眼睛按钮，可以隐藏金额
